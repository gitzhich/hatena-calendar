# revise-design-doc

設計文書に修正指示を反映する。**構成の正はテンプレート**（章立てが決まっている体系ならそれ）、**事実の正は正本リポジトリ**（スキーマ定義・区分値定義・契約定義）。

**文書は正本の複写先ではなく、その対象固有の差分だけを書く場所。**

修正後のレビューは `review-design-doc` が担う（本スキルは書き換え係）。

## 引数

- `<文書 path>` ＋ 修正指示（会話での指示 / レビュー指摘の引用）
- 複数文書可（各文書を独立に STEP 1〜4 で処理）
- 指示が「どのセクションのどの記述を何に変えるか」に落とせないほど曖昧なら、**編集前に**ユーザーへ確認する

---

## 絶対原則（4 つ）

1. **簡潔に書く**: 実装に必要な情報を落とさず最短で。前置き・言い換え・装飾を書かない。
   **ただし下限は「記載粒度・実装可能性」** — 簡潔化を理由に、条件節・エラーコード・端数処理の位置・評価タイミング・初期値といった**実装判断材料を削らない**。
2. **他正本の記載を複写しない**: 列一覧・型、enum の値一覧、契約のスキーマ・エラーコード表、共通規約の本文を文書に転記しない。**参照で済ませる** — 共通設計はアンカーリンク、スキーマ・コードはテーブル名 / カラム名 / コード名の言及のみ。文書に書くのは**その対象固有の差分・使い方**（何を読む条件か・何を書く値か・規約からの逸脱）だけ。
3. **旧記載の跡形を残さない**: 完全置換。「（旧）」「変更前は」「~~取り消し線~~」「※以前は…」等の履歴的記述を本文に残さない（**履歴は git が持つ**）。修正で無効になった記述が**同ファイルの他セクション**に残っていないか、旧キーワードで grep して掃討する。
4. **同じことを二度書かない**: 1 事実 1 箇所。体系が定める正位置（エラー条件・トランザクション境界・テーブル操作・計算）に一度だけ書き、他セクションからは**名前で参照**する（コード名・テーブル名・セクション番号）。「新記述を追記して古い記述も残る」重複を作らない。

---

## 読み取り規律

- **読む**: 指定された文書（全文）・章立てのテンプレート・修正が触れる正本の該当箇所（`ctxray grep` で節単位）
- **読まない**: 指定以外の同種文書（「他の書き方を参考に」をしない — 構成の正はテンプレート）
- 横断文書（共通設計・業務知識・禁止項目一覧）は、まず `ctxray grep` で該当節を引く（アンカーの実在確認・節の把握はこれで足りる）。横断的な整合確認が要るときは全文を読んでよい
- **本質は「読んだ内容を文書へ複写しないこと」**（原則 2）であって、読む量の制限ではない

---

## STEP 0: 正本の鮮度確認

修正の突合先が古いと「**古い正本に合わせて直す**」事故になるため、最初に必ず行う。

1. 参照している正本リポジトリ（submodule / 別 clone）を fetch し behind を確認する:
   ```bash
   git submodule status                                        # '-' 未初期化 / '+' ズレ
   git -C <path> fetch -q
   git -C <path> rev-list --left-right --count HEAD...origin/HEAD
   ```
2. behind のものは fast-forward で更新する（`pull --ff-only`。detached にする `--remote` は使わない）。
   - **改行破損の疑いがあるリポジトリは pull 前にチェックする**: `git status` で modified 多数 → `git diff | cat -A` が全行 `^M$`（本文一致・末尾 CR のみ）なら改行破損＝実内容ゼロなので破棄してから pull する
   - stash 退避が要る実編集・参照の壊れなど込み入った状況は `sync-generated` の手順に従う
3. **責務外**: 生成器の再実行・生成物の追従はしない（必要なら別途 `sync-generated`）。**pull で親リポジトリの submodule ポインタが dirty になるのは想定内 — コミットしない。**
4. **対象文書のリポジトリ自体**は fetch して behind ならユーザーに報告のみ（未コミット編集が常在することがあるので勝手に pull しない）。

---

## STEP 1: 対象文書と修正指示の理解

- 対象文書を全文 Read する。**突合キー**（`operationId` / 機能 ID など、自動処理が使う識別子行）を控える — **消さない・書式を変えない。**
- 修正指示を「§N のこの記述 → こう変える」の**編集計画**に落とし、**波及先を洗い出す**（業務フローを直せば、使用テーブル・業務エラー・トランザクション境界・テスト観点も古くなる）。
- **ファイル名変更・フォルダ移動を手でやらない** — 自動化スクリプトがある体系ではそれが責務。名前が変わる修正では文書内の識別子行を直し、スクリプトの実行を案内する。

---

## STEP 2: 正本突合（修正が触れる範囲だけ）

編集で書く事実は、**書く前に正本を開いて確認する**（記憶・指示文の丸写しで書かない）。

| 書く内容 | 正本 | 確認方法 |
|---|---|---|
| テーブル・カラム・型・NULL 可否 | スキーマ定義 / DB 設計文書 | `ctxray grep <テーブル名>` |
| enum 値・区分値 | 区分値の定義（`code_master` / `enums` / `constants` 等） | `ctxray grep <区分名>` |
| 契約の識別子・リクエスト / レスポンス項目 | API スキーマ | `ctxray grep <識別子>` |
| エラーコード | エラーコード定義（生成物があればそれ） | `ctxray grep <コード>`。**表記規則**まで確認 |
| 共通設計のアンカー | 横断文書 | `grep -n '{#...}'` で実在確認 |

参照リンクを張る（＝複写しない）ときは、**リンク先アンカーの実在確認が生命線**。dangling 参照を作らない。

---

## STEP 3: 編集

- Edit で**完全置換**（原則 3）。テンプレートの見出し・番号・表の列構成を崩さない。
- **波及順に整合させる**: 業務フロー → 使用テーブル（CRUD） → 業務エラー → トランザクション境界 → テスト観点。**1 箇所直して他が古いまま、が「跡形」の典型。**
- 横断文書側を修正する場合: **アンカー名の変更・削除は全参照元を壊す。** 事前に `grep -rl '#<アンカー>' <文書ルート>` で参照元を数え、ユーザーに報告してから行う。
- md の書き込みは Edit / Write を使う。**シェルのヒアドキュメントで書かない**（クォートなしだとバッククォートがコマンド置換され、静かに空文字になる）。

---

## STEP 4: セルフ検証（機械的チェック）

1. **旧記載の掃討**: 修正前の固有キーワード（旧コード・旧テーブル名・旧値・旧条件の言い回し）で対象文書を grep → **0 件**
   - 規約を変えたときは、規約名だけでなく**旧規約に従った実例**で grep する（命名規約なら旧形式の具体名、パス規約なら旧パス）
2. **重複検出**: 今回書いた条件・数値・コードが 2 セクション以上に**本文として**書かれていないか（名前参照は可）
3. **リンク検証**: 追加・変更した相対リンクの**ファイル実在＋アンカー実在**を確認
4. **構造保全**: 突合キー行と章見出しが揃っているか（`grep -E '^## [0-9]+\.|^<識別子キー>'`）
5. **差分確認**: `ctxray diff` または `git -C <repo> diff -- <文書の相対 path>` で**意図した編集だけ**が入っているか確認（改行コードの混入もここで見える）

検証時の注意:

- **`grep ... || echo "0 件"` は「本当に 0 件」と「実行失敗」を区別できない。** 対象ファイルの存在を先に確認する。
- Bash の cwd はツール呼び出しごとにリセットされるので**絶対パスを既定**にし、`cd` と後続は `&&` で繋ぐ。
- **置換後は「置換できた」ではなく「意図した文字列が入った」を grep で確認する。**

---

## STEP 5: 報告

- **セクション別の変更サマリ**（§N: 何を → 何に）
- **確認したが変更不要だった箇所も明示する**（黙って飛ばさない）
- git 操作（branch / commit / push）は本スキルでは行わない。案内のみ。レビューは `review-design-doc` に渡す。

---

## 注意

- 改行コードの統一（`.gitattributes`）に従う。持ち込まない。
- **レビュー指摘の文をそのまま文書に貼らない** — 指摘は編集の**入力**であって記載内容ではない（原則 1・2）。
- 文書の記述と正本が食い違っていて**どちらが正か判断できない**場合は、編集せずユーザーに判断を仰ぐ（**勝手に正本へ寄せない** — 意図的な乖離が存在することがある）。

---

## 設計意図

- **4 原則にそれぞれ「下限」を置いた**: 「簡潔に」だけを指示すると、実装判断材料（条件節・端数処理の位置・評価タイミング）まで削られる。削ると文書は読みやすくなるのに**実装できなくなる**ので、簡潔さの下限を「記載粒度の観点を満たすこと」に固定した。原則は方向だけでなく、行き過ぎの境界も持たせる。

- **正本を複写しない理由**: 複写した瞬間から二重管理が始まり、正本が動いても文書は動かない。しかも読み手には**どちらが正か分からない**（文書のほうが手近なので、古い記述が採用される）。参照だけにすると、正本が動いたときに文書は自動的に正しいままになる。**そのために「読む量」は制限しない** — 正本を読んで理解し、書くのは差分だけ、が正しい形。

- **旧記載の跡形を残さない（履歴は git が持つ）**: 「（旧）」「変更前は」を本文に残すと、文書が改訂履歴を兼ね始めて肥大し、**現在の仕様がどれか分からなくなる**。履歴が要るなら git log を見ればよい。そして跡形は同じファイルの**他セクション**に残ることが最も多いので、旧キーワードでの grep 掃討を手順に固定した。

- **波及順を固定した理由**: 修正は 1 セクションで済むことがほとんど無い。業務フローを直せば、使用テーブル・エラー・トランザクション・テスト観点がすべて古くなる。**上流から下流の順で整合させる**と 1 パスで済むが、順序を決めずに触ると同じセクションを何度も往復し、そのうち 1 つが古いまま残る。

- **1 事実 1 箇所**: 同じ条件を複数箇所に書くと、次の修正でどちらか片方だけが更新される（100% 起きる）。正位置を体系で決めておき、他からは名前で参照する形にすれば、更新箇所が一意になる。名前参照は「情報が減る」ように見えるが、**古い情報が残るリスクのほうが高い**。

- **アンカーを消す前に参照元を数える**: アンカーは複写を避けるための仕組みなので、参照が集中する。名前変更・削除は静かに大量の dangling を作り、**リンクは壊れても誰も気づかない**（表示上は普通のテキストになる）。だから変更前に参照元を数えてユーザーに報告する手順にした。

- **食い違いを勝手に正本へ寄せない**: 文書と正本の不一致は「文書が古い」だけでなく「**意図的な乖離**」であることがある（正本側の更新が追いついていない / 業務上の例外を文書側で表現している）。判断できないまま寄せると、意図を消してしまう。編集を止めて聞くほうが安い。

- **レビュー指摘をそのまま貼らない**: 指摘文は「何が問題か」を書いた文章で、仕様の記述ではない。貼ると文書に評価・経緯・レビュアーの推論が混ざり、原則 1・2 を両方破る。指摘は編集の入力として読み、**出力は仕様の記述に書き直す**。
