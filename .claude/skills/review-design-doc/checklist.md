# review-design-doc チェックリスト

`SKILL.md` から参照する詳細。文書の記述を **tracked な正本**と突き合わせる。未追跡ファイル（作業メモ・ローカル計画書・TODO）は使わない。

---

## 正本マップ（観点 → 突き合わせ先）

**このプロジェクトでの実ファイルパスを最初に埋めてから**使う。埋まらない行は「不明」と明示する（推測で埋めない）。

| 用途 | 正本の探し方 | 注意 |
|---|---|---|
| テーブル・列・型・NULL 可否・UNIQUE・バージョン列 | スキーマ定義ファイル。**DB 設計文書が別にあるならそちらが正本**で、実装側スキーマはドリフトしうる | 両方見て食い違ったら設計文書側を正とし、ドリフトとして記録する |
| enum・区分値・表示ラベル | 区分値の定義（`code_master` / `enums` / `constants` 等）、または生成された定数ファイル | 値域・キーの型（数値 / 文字列）・状態数を見る。**表示ラベルやシード投入フラグを持つ体系なら、値域だけでなくラベルと投入対象の追従も要る**（enum より広い） |
| エラーコードとステータス | エラーコード定義（生成物があればそれ） | **表記規則**（kebab / snake / 大文字）まで確認。表記違いは実装時に必ず割れる |
| 契約（リクエスト / レスポンス） | API スキーマ、または生成された型定義 | 契約から削除された拡張（`x-` 系）を文書が参照していないか |
| 認証主体・認可の仕組み | 認証まわりのソースとその冒頭コメント | 「主体種別」と「権限ロール」が**別の軸**であることが多い。混同に注意 |
| 採用しない方針・暗号・ログの個人情報規則 | ルート `CLAUDE.md` / `AGENTS.md` | 「採用しないもの」表に反する設計になっていないか |
| 横断規約・参照アンカー | 対象文書と同じ体系の共通設計文書 | これは**入力**でもある（per-機能 文書と同じ一式） |

## 焼き込み知識（ここを正とし、最終は実体で再確認）

技術非依存で効く定石。プロジェクトの実体（分離レベル・DB 製品・ジョブ基盤）で必ず裏を取る。

### 並行制御

- **既定の分離レベルを確認する。** READ COMMITTED では `SELECT ... FOR UPDATE` は**存在しない行をロックしない**（ギャップロックが無い）。
  - **新規行の並行制御の実ガードは UNIQUE 制約**（重複 INSERT → 一意制約違反を捕捉して 409）
  - **既存行の更新競合は楽観バージョン**（`WHERE id = ? AND version = ?` の条件付き UPDATE、0 件なら 409）
  - INSERT / UPDATE 両方ある upsert は「UNIQUE（新規）＋ 状態 + バージョン条件付き UPDATE（更新）」の二本立て
- 悲観ロックが要るのは「読んだ行を確実に更新するまで他を待たせたい」場合だけ。

### 非同期・分散ジョブ

一般のトランザクション整形は後述の手順 A。ここは「別プロセス・長時間・起動」に固有のものだけ。

- **外部 I/O・外部タスク起動（ファイル生成・ストレージ・HTTP・メール・ジョブ起動）も、重い処理（大量計算・ループ）もトランザクションの外。** トランザクションは確定する書き込みだけを最小で囲う。
- **起動の信頼性（孤児ジョブ）**: ジョブ行の作成と worker 起動が別操作なら、**起動失敗で行が中間状態のまま取り残される**。起動を fire-and-forget にせず、起動とジョブ行を結ぶ仕組み（キュー / イベントバス / outbox）＋リカバリーバッチで回収する。
- **worker 死亡（固まりジョブ）**: 中間状態のまま worker が落ちた行を、一定時間進まなければ失敗へ倒す / 再投入するリカバリーバッチ。
- **別プロセスの楽観更新**: worker は更新直前に対象行の現在バージョンを読み直してから条件付き UPDATE する（呼び出し元が発行したバージョンの使い回しは衝突する）。

### 端数処理

- 「切り捨て / 四捨五入」だけでは足りない。**どの計算段階で適用するか**（明細 → 個人 → 月次合計）が無いと 1 単位ずれる → 粒度ギャップとして指摘する。

## 観点 8 系統

### ① 基盤整合（正本突合）

- **エラーコード**: 文書のコードが定義に**実在**するか / **表記規則**が合っているか / ステータスの対応が一致するか。
- **テーブル・列**: 参照している table / column がスキーマに実在するか（型・NULL 可否・UNIQUE・バージョン列の初期値）。
- **enum・区分値**: 値域・キーの型・状態数が定義と一致するか。
  **値域が「運用でデータとして増える」体系か「変更にリリースが要る」体系かを区別する** — 前者なら文書は未知の値に対する挙動（既定値 / 拒否）を定義していなければならず、網羅的な分岐に頼れない。表示ラベルやシード投入フラグを持つ定義は前者の性質を帯びる。
- **認証主体・認可**: 主体種別が定義の集合に収まるか。**権限を識別子の名前分岐で書いていないか**（正がデータ駆動なら、ガード側のハードコード例外は存在しないはず — 例外扱いも設定データ側で表現される）。
- **採用しない方針**: 「採用しないもの」表に反していないか。

### ② 記載粒度・実装可能性

- **状態が「保存値 or 導出値」か明示**されているか。導出なら**式**＋**評価タイミング**（読み取り時計算 / バッチ更新）。
  - 判定: 該当テーブルに状態列があるかスキーマで確認する。無ければ導出のはず。
- 計算に**条件 → 値の決定表 / 対応表**があるか（式だけでは足りない）。
- **端数処理の適用ポイント**を計算段階ごとに明示しているか。
- **参照元（データの出どころ）**を明示しているか。
- **「共通基盤が自動でやる」への委任の形が正しいか**（基盤が未実装でも flag しない。委任の形だけ見る）。
- 関連データ初期化の**初期値**。
- **クライアント指定の識別子の異常系**（存在しない / 論理削除済み / 別スコープ）の挙動が定義されているか。
- **契約で null 許容なフィールドは `null` と「キー省略」が別物。** 文書が「省略 → 新規作成」等を書くなら、**明示的な null** の扱いも定義されているか。

### ③ 契約整合

- レスポンス各フィールドの**出どころが「使用テーブル」で賄えるか**（読み取り不足の検出）。
- **enum の値域がマスタと一致**しているか（例: 文書が 3 値、マスタが 4 値）。
- リクエスト / レスポンスに**フィールドが在るか**（文書が返すと書いているものが契約型に無い、等）。
- パス・識別子・突合キーが契約と一致しているか。

### ④ トランザクション・並行 ★最優先

正本との機械的ズレだけでなく**「実際に動かしたときの破綻」**を必ず詰める。文書がトランザクションを記述していたら手順 A〜C を**番号順に全部**実行する（soft に眺めて終わらせない）。

**手順 A — トランザクション範囲の最小化**（文書が「tx 内ステップ」を列挙していたら必須）

1. tx 内 / 外と書かれた各ステップを、**1 つずつ read / write を明記した表に起こす**。「tx 内 = 4〜9 で妥当」のような**塊での判定で済ませない** — 必ず各ステップ番号ごとに read か write を書く。SELECT・前提チェック・データ整形 = read／INSERT・UPDATE・DELETE = write。**「更新用データ作成」「マッピング」「整形」等の曖昧な名前のステップは本文を開いて read か write か確定する**（名前で write 群に丸めない）。
2. **read-only ステップが tx 内にあれば指摘。** tx を伸ばすだけで一貫性に寄与しない。tx は **write を含む最小連続区間だけ**。前提チェックの SELECT は原則 tx 外（先勝ちは UNIQUE で担保する）。
3. **write が 1 つだけなら明示 tx を貼らない。** 単一の INSERT / UPDATE は**それ自体が原子的**（途中状態が無い）ので、1 文を tx で囲っても何も守らない。tx が意味を持つのは **2 つ以上の write を「全部成功 or 全部ロールバック」でまとめたいときだけ**。単一 write を tx で囲っていたら「tx 不要」、複数 write が散っていたら「まとめて 1 tx」と指摘する。
4. **外部呼び出し（タスク起動・ストレージ・メール・他 API）が tx 内にあれば指摘。** コミット前の外部副作用、または外部待ちで長時間 tx になる。
5. **「各個別 tx」「〜ごとに tx / commit」のような反復コミットがあれば必ず指摘。** 外部 I/O が tx 外で正しくても、それに釣られて "OK" で流さない — **書き込みが反復ループ内でコミットされていれば部分コミット**になり「全成功 / 全失敗」に反する。確定 write は**最終 1 tx に集約**する。

**手順 B — 並行ガードの主役を正す**

- 新規行の競合 = **UNIQUE 違反が主役**。文書が「行ロックで並行制御」と書き、対象が **INSERT のみ**なら**その行ロックは無意味＝指摘**（「行が無いのでロック対象が存在しない」と明記する）。
- 既存行の競合 = **楽観バージョン**（0 件なら 409）。
- 文書の検索条件がスキーマの UNIQUE と一致するか。ズレていれば**「並行が成立しない」or「多重実行できる」を具体に**書く。
- 並行制御が**トランザクション節だけでなく業務フロー節にも明示**されているか（tx 節だけにあると実装の手順から漏れる）。

**手順 C — upsert / 再実行 / 初期値**

- 「一度きり」か「再実行あり（再確定・上書き）」かを判定する。INSERT 固定で書いてあるのに再実行運用があれば、**INSERT（UNIQUE ガード）＋ 既存行の条件付き UPDATE（バージョン）**の二本立てに直す。
- INSERT 時のバージョン初期値がスキーマの既定値と一致するか。固定値を書いていて再実行・並行で衝突しないか。

### ⑤ セキュリティ

- **主体の列挙**（認証で「未存在 / 不一致 / ロック」の応答が分岐していないか。タイミングオラクルも）。
- **IDOR**: クライアント供給の識別子を**対象スコープ**で検証するか。**更新 / 削除系は取得の検索条件だけでなく、実際の UPDATE / DELETE の条件節にもスコープを入れる** — 取得で絞っても書き込みが識別子単独なら別スコープの行を書き換えられる。
- **自己操作制約**（自分のアカウントを削除 / 権限変更できない等）がある文書では、(a) 制約の**対象範囲**（権限変更だけか、基本情報の編集まで禁止か）と (b) **例外**（管理者は自分を変更できるか）を**要決定**として挙げる（未定義なら粒度ギャップ）。
- **ログの個人情報禁止**（監査ログの要約に識別子と分類語だけを入れる規則になっているか）。**検索語も個人情報になりうる**（氏名の断片が検索条件に入る）。
- 機微情報の除外（ハッシュ・トークンを**返さない / 読まない**設計か）。
- 認可の **fail-open**（宣言の誤付与・宣言と allowlist の 2 点セット崩れ）。※ 未実装のガードは除外。

### ⑥ 非同期・バッチジョブ ★最優先

焼き込み知識の定石を文書に重ね、**起動・worker・復帰の 3 点**を必ず詰める。

1. **起動の信頼性（孤児ジョブ）**: ジョブ行の作成と worker 起動が別操作なら、**起動失敗でジョブ行が処理中のまま取り残される**。起動が inline / fire-and-forget なら**指摘**し、**キュー / イベントバス / outbox 経由**（起動とジョブ行を確実に結ぶ）か**リカバリーバッチでの回収**を要求する。「fire-and-forget ＋リカバリー」を見ても "OK" で流さず、起動失敗時に行が残る経路を点検する。
2. **worker 死亡（固まりジョブ）**: **一定時間進まない処理中の行を失敗へ倒す / 再投入するリカバリーバッチ**があるか。
3. **状態復帰**: 失敗の捕捉で**終了状態を確実に書く**。worker のどの段階で落ちても状態が宙に浮かない設計か。
4. **バージョンの取得経路**: 別プロセスが楽観更新するなら、**更新直前に現在バージョンを再取得**する手順が書かれているか。同期側で発行したバージョンの使い回しは衝突する。
5. **tx 粒度**: ジョブ全体や反復ループを 1 tx で包まない（長時間 tx 禁止）。外部 I/O は tx 外。確定書き込みだけを最終 1 tx にまとめる（→ 手順 A）。行ごとの個別 tx もしない。
6. **全成功 / 全失敗**・中途半端なコミットをしない（5 と両立する範囲で）。
7. **状態の語彙の一致**（区分値定義 / 契約 / 文書で同じ語を使っているか）。

### ⑦ 共通ルール整合

- 対象文書が横断文書の規約に従っているか（エラーコード・ログの形・ページネーション・ソート・命名・端数処理）。
- **参照アンカーが実在するか**（dangling 検出）。
- 数値・状態数の不一致（例: 回数の閾値が文書間で違う、状態が 2 か 3 か）。

### ⑧ 整合性・重複・用語

- **業務フロー節 ↔ CRUD 節のドリフト**（片方が古い）。
- 用語の揺れ（略称と正式名が混在）。
- 状態の保存先・キー名の一貫性。

## 除外ルール（横断基盤の「未実装」は指摘しない）

別途実装が進行中の**横断インフラ部品の「まだ無い」は指摘しない**。典型: 認可ガード / 例外フィルタ / 出力の機密除外 / 監査ロガー本実装 / レスポンス整形・ページネーションの共通層 / 入力補正（trim・全角半角・0 埋め）。

**境界**: 「基盤がまだ無い」≠ 指摘 ／ 「文書が基盤を**誤って前提 / 誤った形で使っている**」= 指摘。

| 状況 | 扱い |
|---|---|
| 認可ガードが未実装 | **除外** |
| 文書が認可を識別子の名前分岐で書く（正はデータ駆動） | **指摘** |
| 出力の機密除外機構が未実装 | **除外** |
| 文書が機密フィールドをレスポンスに含める設計 | **指摘** |
| 監査ログの項目を**誤ったテーブルに帰属**させている | **指摘** |
| 主体種別に定義外の値を使う | **指摘** |

→ 「実装が在るか無いか」はソースを `ctxray grep` / Read で**確認してから**判断する（計画文書は見ない）。

## smell 例（過去パターン。現状のバグではなく「チェックすべき型」。毎回正本で再確認）

- エラーコードの**表記規則が違う**（snake / kebab / 大文字の取り違え）
- エラーコードが**定義に未登録 / typo**
- **行ロックを RC で並行制御の主役にしている**（INSERT のみ＝ロック対象の行が無く無意味）
- **tx 内に read-only ステップ（前提 SELECT・整形）を入れて範囲が広い**
- **単一 write を明示 tx で囲う**（無意味）／**複数 write が別々の tx に散っている**（最終 1 tx にまとめるべき）
- **タスク起動を fire-and-forget** → 起動失敗でジョブ行が処理中のまま**孤児**化
- **worker がバージョンを取り直さず**同期側で発行した値を使い回す → 楽観更新が衝突
- **ジョブ全体を 1 tx で包む**（重い生成処理・外部 I/O を含む長時間 tx）
- 状態を**保存値前提**で書くが実は導出（状態列がスキーマに無い）
- 計算が**決定表欠落**（式だけあって条件 → 値の表が無い）
- enum の値域がマスタと不一致
- 監査ログの項目を**誤ったテーブルに帰属**
- **更新 / 削除で取得はスコープ絞りだが書き込みの条件節が識別子単独**（越境して書き換えられる）
- セッション・トークンの失効漏れ（退職 / 権限変更時に一部だけ失効）
- 状態の語彙の不一致（done/error vs succeeded/failed vs queued/running）
- 採番に行ロックを使うが分離レベルで効かない（実ガードは UNIQUE）

## 出力形式

- **severity**: 🔴ブロッカー（このままでは実装不能）/ 🟡整合性（正本とズレ）/ 🟢粒度（実装に入れない・曖昧）/ ⚠️要決定（設計判断が要る）
- 各指摘: **根拠（正本の `file:symbol`）＋ 何が違うか ＋ 直し方**
- **粒度ギャップ**には「この見出しの下に足すべき観点」（導出式 / 参照元 / 端数処理の位置 / 決定表 / 初期値 / 評価タイミング）
- 末尾に**「確認したが問題なし」の観点**も 1 行で（黙って飛ばさない）
- `--md` 指定時は同内容をファイルに書き出す（ハンドオフ用）
