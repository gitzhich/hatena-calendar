# review-design-doc

実装前の設計文書を「実装できるか / 既存基盤と整合するか」で精査する。**文書を読むだけで終わらせず、各記述を tracked な正本ファイルに突き合わせる**のが本スキルの核。

## 引数

- `<文書 path>` → その 1 本を精査（**既定モード**）
- `<dir>` → 配下の文書を一括（**バッチ**）
- 末尾 `--md` → 指摘を md ファイルに書き出す（既定は会話に表示）

---

## 絶対原則（5 つ）

1. **正本突合**: 文書の各記述を、対応する正本ファイルを**開いて diff** する。「文書にこう書いてある」で終わらせない。
2. **tracked のみ依存**: git 未追跡のファイル（作業メモ・ローカルの計画書・生成前の中間物）は**読まない・存在を前提にしない**。正本は [checklist.md](./checklist.md) の「正本マップ」に挙げた tracked なものだけを使う。
3. **実装の有無はコードで確認**: 基盤・共通部品が実装済みかどうかは、ソースを `ctxray grep` / Read で**実体確認**する。TODO・計画文書・チケットを信用しない。
4. **adversarial verify**: 各指摘は「本当に問題か、正本で再確認」してから出す。憶測・記憶ベースの指摘を出さない（行番号・列名・定数名も毎回開いて確認）。
5. **未実装は指摘しない / 誤用は指摘する**: 別途進行中の横断基盤の「まだ無い」は**除外**。ただし文書が基盤を**誤って前提にしている / 誤った形で使っている**のは指摘する（境界は [checklist.md](./checklist.md) の境界表）。

---

## STEP 0: 正本と文書の鮮度チェック（最初に必ず・fail-fast）

ローカルが古いと**古い正本 / 古い文書に対してレビューしてしまう**。読む前に確認する。

1. **submodule**: `git submodule status` の先頭フラグを見る。
   - `-`（未初期化）→ 正本が空＝**レビュー不能**。`git submodule update --init --recursive` を促して中断する
   - `+`（superproject の記録と checkout がズレ）→ 注意喚起
   - ` `（一致）→ OK
2. **別 clone / 参照リポジトリ**（レビュー対象文書のリポジトリを含む）:
   ```bash
   git -C <path> rev-parse --show-toplevel        # 対象文書のリポジトリを解決
   git -C <path> fetch -q
   git -C <path> rev-list --left-right --count HEAD...origin/HEAD
   ```
3. **古いものがあれば勝手に更新せず**、「何が・どれだけ古いか」をユーザーに報告し、更新してから進めるか／承知で続行するかを確認する。`-`（未初期化）以外は続行可。

---

## STEP 1: 対象文書を読む

- 対象文書 ＋ **同じ体系の横断文書**（共通設計・業務知識・規約集）を読む。横断文書は参照アンカーの正本でもある。
- 突合キー（`operationId` / 機能 ID / API 名など、文書と契約を結びつける識別子）を控える。

## STEP 2: 正本をロードする（tracked のみ・必要分だけ）

[checklist.md](./checklist.md) の「正本マップ」に従い、**このプロジェクトの正本を実ファイルパスで確定させてから**読む。典型:

| 用途 | 正本の探し方 |
|---|---|
| テーブル・列・型・NULL 可否・制約 | スキーマ定義ファイル（DB 設計文書があるならそちらが正本で、実装側スキーマは**ドリフトしうる**） |
| enum・区分値・表示ラベル | 区分値の定義（`code_master` / `enums` / `constants` 等） / 生成された定数ファイル |
| エラーコードとステータスの対応 | エラーコード定義（生成物があればそれ）。**値の表記規則**（kebab / snake / 大文字）まで確認する |
| 契約（リクエスト / レスポンス） | API スキーマ、または生成された型定義 |
| 認証主体・認可の仕組み | 認証まわりのソースと、その冒頭コメント |
| 採用しない方針・暗号・ログの個人情報規則 | ルート `CLAUDE.md` / `AGENTS.md` |
| 横断規約・参照アンカー | 対象文書と同じ体系の共通設計文書 |

## STEP 3: 観点 8 系統でチェックする

[checklist.md](./checklist.md) の観点①〜⑧を上から当てる。各観点が指定する正本を突き合わせる。

- **文書がトランザクション / 並行 / 非同期ジョブを含むなら、観点 ④⑤⑥ を最優先**とし、checklist の**手順 A〜C と 1〜7 を番号順に全部実行**する。ここは「正本との機械的ズレ」だけでなく**動かしたときの破綻**（トランザクション範囲・孤児ジョブ・固まりジョブ・バージョン取得・状態復帰）を詰める。**soft に眺めて "OK" で流さない**（最も指摘が漏れやすい）。

## STEP 4: adversarial verify ＋ 除外

- 各候補指摘を正本で再確認する。確証が無い / 既に直っているものは落とす。
- 横断基盤の未実装は除外（原則 5）。ただし「実装が在るのに文書の使い方がズレている」は、**ソースで実装を確認した上で**指摘する。

## STEP 5: 出力

- **severity**: 🔴ブロッカー（このままでは実装不能）/ 🟡整合性（正本とズレ）/ 🟢粒度（実装に入れない・曖昧）/ ⚠️要決定（設計判断が要る）
- 各指摘: **根拠（正本の `file:symbol`）＋ 何が違うか ＋ 直し方**
- **粒度ギャップには「この見出しの下に足すべき観点」を提示**する（導出式 / 参照元 / 端数処理の位置 / 決定表 / 初期値）
- 末尾に**「確認したが問題なし」の観点**も 1 行で（黙って飛ばさない）
- `--md` 指定時は同内容をファイルに書き出す（ハンドオフ用）

---

## バッチ（複数文書）

`<dir>` 指定時は **STEP 0 を最初に 1 回**実行し、その後は文書ごとに独立して STEP 1〜4 を回して、最後に統合した指摘を出す。
※ 複数エージェントでの並行実行（Workflow / Agent）は**ユーザーが明示的に許可しているときだけ**使う。文書が多いときに「並行で一括しますか？」と提案する。

---

## 注意

- **「指摘が無い」と「確認した」を区別する。** 確認したが問題無し、を明示する（黙って飛ばさない）。
- 文書も正本も腐る。**行番号・列名・コードは記憶でなく毎回開いて確認する。**
- コード diff が対象の `review-diff` とは目的が違う。本スキルは**実装前の文書**が対象。
- 精査後の書き換えは `revise-design-doc` が担う（本スキルは読むだけ）。

---

## 設計意図

- **突合を核に置いた理由**: 設計文書は「それ自体としては筋が通っている」ことがほとんどで、通読レビューでは何も見つからない。壊れているのは**文書と正本の間**（実在しない列を参照している / enum の値域が古い / エラーコードの表記が違う / 契約に無いフィールドを返すと書いている）で、これは開いて突き合わせる以外に検出手段が無い。だから「読む」ではなく「突き合わせる」を手順の中心にした。

- **tracked のみ依存**: 未追跡ファイル（作業メモ・ローカル計画書・TODO）を根拠にすると、**レビュアーにしか見えない前提**で指摘を出すことになり、受け取った側が検算できない。さらにその内容は往々にして古い。正本を tracked なものに限ると、指摘が誰でも再現できる形になる。

- **実装の有無はコードで確認する**: 「TODO に未実装と書いてある」を信じると、既に実装済みのものを「未実装」として除外してしまい、**本当は指摘すべき誤用を見逃す**。逆に「実装済みと書いてある」を信じると、存在しない基盤を前提にした文書を通してしまう。計画文書は必ず現実より遅れているので、ソースを見る。

- **「未実装」と「誤用」の境界を先に決める**: この境界を決めずにレビューすると、進行中の基盤について「まだ無い」を大量に指摘してノイズだらけになり、肝心の指摘が埋もれる。一方で全部除外すると、**文書が基盤を誤った形で使っている**という最も重要な種類の指摘が消える。だから境界表（未実装は除外 / 誤った前提・誤った使い方は指摘）を明文化し、判定を裁量に任せない。

- **トランザクション・並行・非同期を最優先にした理由**: この 3 つは**正本と突き合わせても検出できない**。スキーマにも契約にも「この順で書くと部分コミットになる」は書かれていないので、動かしたときの破綻を頭の中で再生する必要がある。しかも壊れ方が静かで（普段は動く・負荷や失敗時だけ壊れる）、実装後のレビューやテストでも見つからない。**実装前が最後の検出機会**なので、手順を番号付きで固定して soft に流せないようにした。

- **手順 A で「read/write の表に起こす」を強制する**: 「tx 内 = ステップ 4〜9 で妥当」のような**塊での判定**は、ほぼ必ず read-only ステップを巻き込んでいる。ステップ名（「更新用データ作成」「マッピング」「整形」）は read か write かを隠すので、名前で判断せず本文を開いて確定させる。表に起こすと「read-only が tx 内にある」「write が 1 つしかない」が機械的に見える。

- **粒度ギャップに「足すべき観点」を添える**: 「曖昧です」だけでは書き手が何を書けばいいか分からず、次の版でも同じ曖昧さが残る。**足すべき観点の型**（導出式なのか保存値なのか / 評価タイミング / 端数処理をどの段階で適用するか / 決定表 / 初期値 / 参照元）を示すと、1 往復で埋まる。

- **「確認したが問題なし」を必ず書く**: 書かないと、読み手は「その観点は見た結果 OK」と「そもそも見ていない」を区別できない。区別できないレビュー結果は、実装 GO の判断材料に使えない。
