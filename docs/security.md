## 1. この文書の位置づけ

[CLAUDE.md](../CLAUDE.md) の「セキュリティ方針」が**実装時に守るルール**であるのに対し、
この文書は**なぜそれが必要か（脅威）**と**起きたときの手順**を扱う。

### 1.1 このアプリの特徴

一般的な Web アプリとリスクの重心が違う。

- **個人情報をほとんど扱わない。** 閲覧者アカウントが存在せず、
  管理者は 1 人。DB に保存される個人情報は実質ゼロ
- **機密性より完全性が重要。** 公開している情報はすべて公式 X で既に公開済み。
  盗まれて困るデータはない。一方で**誤った出演情報が公開されると、
  ファンが実際に会場へ足を運んで会えない**という実害が出る
- **金銭被害の経路がある。** X API は従量課金であり、
  Bearer Token が漏れると第三者に課金される

したがって優先順位は **① 認証情報の保護 → ② 公開データの完全性 → ③ 可用性** となる。

## 2. 守るべき資産

| 資産 | 漏洩・侵害時の影響 | 優先度 |
| --- | --- | --- |
| X API の Bearer Token | **第三者に課金される**。従量課金のため金額が青天井 | 最高 |
| 管理用の内部 API キー | 管理操作が通り、誤情報を公開される | 最高 |
| 管理者パスワード | 同上 | 最高 |
| DB 接続文字列 | データの改ざん・削除 | 高 |
| セッション Cookie の署名鍵 | 管理者になりすませる | 高 |
| 公開データの正確性 | **ファンが誤った会場・日時に行く** | 高 |
| サイトの可用性 | ファンが予定を確認できない | 中 |
| 閲覧者の個人情報 | 収集していないため該当なし | — |

## 3. 脅威と対策

### T-01 X API トークンの漏洩による課金被害

**最も金銭的損害が大きい脅威。**

| 侵入経路 | 対策 | 実装箇所 |
| --- | --- | --- |
| リポジトリへの誤コミット | `.gitignore` で `.env*` を除外。`.env.example` は値を伏せる | ルート `.gitignore` |
| ログへの出力 | トークンをログに出さない。ログ出力前にマスクする | Spring Boot のログ設定 |
| エラーレスポンス | スタックトレースと内部情報を返さない（NFR-03） | 共通例外ハンドラ |
| フロントエンドへの露出 | トークンは Spring Boot 側のみが保持。Next.js に渡さない | [architecture.md](architecture.md)「設定と環境変数」 |
| 設定ミス | `fly secrets set` で設定し、`fly.toml` に書かない | デプロイ手順 |

**検知**: `ingestion_run.fetched_resource_count` の請求サイクル合計を管理画面に表示する
（[api.md](api.md)「取り込み履歴」）。想定は月 300 リソース程度なので、
**桁違いの増加は第三者利用のサインになる**。

**漏洩時**: 本書「インシデント対応」の手順に従う。履歴からの削除では不十分で、**必ず無効化・再発行する**。

### T-02 管理画面の乗っ取りによる誤情報の公開

承認フローを持たない設計のため、管理操作が通れば**即座に公開される**。

| 侵入経路 | 対策 |
| --- | --- |
| パスワードの総当たり | ログイン試行のレート制限。**Next.js と Spring Boot の両方**に置く（[api.md](api.md)「内部 API」） |
| パスワードの推測 | 十分な長さのランダム文字列を使う。BCrypt で保存し平文を保持しない |
| セッション Cookie の窃取 | `HttpOnly` / `Secure` / `SameSite=Lax`。有効期限 8 時間 |
| 管理 API キーの漏洩 | 公開キーと分離し、Cookie 検証後にのみ使用（[api.md](api.md)「認証」） |
| CSRF | `SameSite=Lax` に加え、管理操作の POST に CSRF トークンを要求する |

**ログイン失敗時にユーザー名の存否を区別できるメッセージを返さない**（FR-20）。
本アプリは単一管理者でユーザー名の概念がないため、
`/internal/auth` は成否をステータスコードで区別せず常に `200` を返す。

### T-03 X 由来のテキストによるインジェクション

**取り込んだテキストは攻撃者が自由に書ける入力**として扱う。
情報源アカウントが乗っ取られた場合、任意の文字列が本文に入る。

| 攻撃 | 対策 |
| --- | --- |
| XSS（スクリプト埋め込み） | React の既定のエスケープに任せる。**`dangerouslySetInnerHTML` を使わない** |
| **`javascript:` スキームのリンク** | URL は `http` / `https` のみ許可。3 層で検証（下記） |
| SQL インジェクション | JPA / パラメータバインドのみ。文字列連結でクエリを組み立てない |
| 極端に長い文字列 | 各列に長さ制限（`CHECK`）とサーバ側バリデーション |

**`javascript:` スキームは実際に起こりうる。** 告知本文に
`🔗javascript:...` と書けば抽出対象になりうるため、次の 3 層で防ぐ。

1. **抽出時**: 正規表現が `https?://` で始まる URL のみを拾う
   （[x-integration.md](x-integration.md)「チケット URL」）
2. **保存時**: DB の `CHECK` 制約（`ticket_url ~ '^https?://'`）
3. **表示時**: リンクを描画する前にスキームを再検証する

どれか 1 つが漏れても他で止まる構成にする。

### T-04 無料枠の枯渇による可用性攻撃

**このアーキテクチャ固有の脅威。**

Neon Free はコンピュート時間 100 CU-hours/月を超えると
**翌請求月までコンピュートが停止する**（[architecture.md](architecture.md)「Neon を選んだ理由と制約」）。
つまり攻撃者が公開ページを連打してリクエストを DB まで到達させ続ければ、
**課金を発生させずにサイトを丸ごと停止させられる**。

| 対策 | 効果 |
| --- | --- |
| 年月の受理範囲を有限にする | **キャッシュキーを無制限に増やされるのを防ぐ。** 範囲外は DB に届く前に `404`（FR-05、[ADR-0014](adr/0014-bounded-calendar-range.md)） |
| 公開カレンダーの ISR キャッシュ | 範囲内で繰り返されるアクセスが Vercel で返り、**DB に届かない** |
| Next.js middleware でのレート制限 | 実クライアント IP で絞る（[architecture.md](architecture.md)「公開ページのレート制限」） |
| CU-hours の定期確認 | 枯渇前に従量課金へ切り替えられる |

**ISR キャッシュだけでは防げない。** キャッシュが効くのは同じ URL が繰り返し
要求される場合であり、`[year]/[month]` の年月を変え続ければ毎回キャッシュミスになって
Neon まで届く。範囲の限定と組み合わせて初めて防御になる。
キャッシュを外す変更を入れる場合は、この脅威を再評価すること。

**レート制限を Spring Boot 側だけに置いても効かない。** そこから見た送信元は
Vercel の egress IP であり、IP 単位に絞ると攻撃者ではなく全閲覧者が
まとめて絞られる（[architecture.md](architecture.md)「経路ごとの保護」と同じ理由）。

**攻撃の余地は残り枠で決まる。** 取り込みジョブ自体が CU-hours の
ベースラインを消費するため（[architecture.md](architecture.md)「運用コストの試算」）、
枯渇までの距離を見るときは 100 CU-hours ではなく**残りの約 69** を基準にする。

### T-05 情報源アカウントの乗っ取りによる偽情報の取り込み

公式 X アカウント自体が乗っ取られた場合、偽の告知が自動で公開される。
承認フローがないため、**取り込みから公開まで人の目が入らない**。

| 対策 | 内容 |
| --- | --- |
| 事後点検 | 管理者が自動登録を定期的に確認する（FR-24） |
| 抽出の保守性 | 定型フォーマットに合致しない投稿は `UNPARSED` にする（[x-integration.md](x-integration.md)「抽出対象の判定」） |
| 削除手段 | 誤情報が判明したら個別削除、必要ならサイト全体を止める（本書「誤った出演情報の公開が判明した場合」。LR-05） |

**これは完全には防げない。** 公式アカウントを信頼する設計を選んだ以上、
検知と復旧の速さで対応する。本書「インシデント対応」の手順に含める。

### T-06 依存パッケージの脆弱性

| 対策 | 対象 |
| --- | --- |
| Dependabot（または同等） | `frontend/` の npm、`backend/` の Maven/Gradle |
| `npm audit` | ローカルおよび CI |
| OWASP Dependency-Check | バックエンドの依存 |

**放置された更新が現実的な最大リスク**であり、
月次で確認する運用を本書「定期的な確認」に置く。

### T-07 リポジトリ公開による情報漏洩

**このリポジトリは外部公開しない。** 公開範囲は運用者本人に限る
（[ADR-0015](adr/0015-private-repository.md)）。

`docs/x-post-sample/` に置いている実サンプルは **X 投稿の本文そのもの**であり、
公開すれば転載にあたる。一方これは抽出ロジックのテストに必要な資産で、
架空のデータに差し替えると**実際の表記ゆれを検証できなくなる**（本書「未決定事項」 / FR-41）。
非公開を前提にすることで、サンプルをそのまま保持できる。

LR-02（投稿本文を転載しない）は**公開されるアプリ**に対する要件であり、
非公開リポジトリ内の開発用フィクスチャはその対象ではない。
アプリ側の受入基準（DB に本文の列がない／画面に本文を出さない）は変わらない。

- **サンプルを追加するたび、コミット履歴に本文が積み上がる。**
  後から公開へ転じるには履歴の書き換えが要るため、この決定は実質的に不可逆
- 公開へ転じる判断をする場合は、**`docs/x-post-sample/` を架空データへ差し替え、
  履歴からも除去する**（`.gitignore` へ移すだけでは履歴に残る）
- リポジトリのホスティング先アカウントが侵害されればサンプルは流出する。
  ただし内容は公式アカウントが公開済みの投稿であり、被害は限定的
- `.env` やシークレットをコミットしない方針は**非公開でも変わらない**（T-01）。
  非公開は多層防御の 1 枚であって、コミットしてよい理由にはならない

## 4. 対策が効く場所の一覧

| 層 | 対策 |
| --- | --- |
| Next.js | セッション Cookie の検証、CSRF トークン、レート制限（ログイン試行・公開ページ）、年月範囲の検証、ISR キャッシュ、サイト全体の停止 |
| Spring Security | デフォルト拒否、API キーの固定時間比較、公開 API は `GET` のみ |
| Bean Validation | 入力値の検証（サーバ側を正とする） |
| DB 制約 | `CHECK`（URL スキーム、長さ、時刻の前後関係）、`UNIQUE`（重複登録の防止） |
| レスポンスヘッダ | CSP / HSTS / `X-Content-Type-Options: nosniff` / `Referrer-Policy` |
| ログ | トークン・パスワードのマスク |

### 4.1 セキュリティヘッダの構成と検証

**CSP は 2 系統ある**（[ADR-0016](adr/0016-static-csp-public-nonce-admin.md)）。

| 対象 | 方式 | 理由 |
| --- | --- | --- |
| 公開ページ | 静的 CSP（`script-src` に `'unsafe-inline'`） | nonce はページを動的レンダリングにし、**ISR を無効化する**。ISR は T-04 の主防御 |
| `/admin` 配下 | nonce ベース（`'nonce-…' 'strict-dynamic'`） | もともと動的レンダリングなので、nonce の代償がない |

**公開ページで緩むのは `script-src` だけ**で、`frame-ancestors` / `connect-src` /
`form-action` / `base-uri` / `object-src` は同じ強さで効く。
公開ページ側の実害は**セッション Cookie の `path` を `/admin` に絞ることで打ち消している**
（T-02）。

置き場所を分けている。**CSP は `proxy.ts` で 1 度だけ付ける。**
`next.config.ts` からも出すと `Content-Security-Policy` が 2 本になり、
ブラウザは両方を同時に適用する（許可の積集合）。
常時付けるヘッダは `next.config.ts` 側で、あちらは静的アセットにも届く。

**検証手順。** 本番ビルドを起動して実際のレスポンスヘッダを見る。
開発サーバとは値が違う（`'unsafe-eval'` の有無、`upgrade-insecure-requests` の有無）ため、
`npm run dev` では確認にならない。

```bash
cd frontend
npm run build && npm start

# 公開ページ: 静的 CSP と常時ヘッダ
curl -sI http://localhost:3000/ | grep -iE 'content-security-policy|strict-transport|x-content-type|referrer-policy'

# 管理画面: nonce があること
curl -sI http://localhost:3000/admin/login | grep -i content-security-policy

# 静的アセット: nosniff が届くこと
curl -sI http://localhost:3000/_next/static/... | grep -i x-content-type-options
```

**nonce が実際にスクリプトへ付いているかまで見る。** ヘッダだけ確認しても、
Next.js が nonce を付け損ねていれば管理画面は動かない。
`/admin/login` の HTML で、`<script` の数と `nonce=` を持つ数が一致することを確かめる。

### 4.2 レート制限の構成と値

**2 層に分かれ、目的が違う**（[architecture.md](architecture.md)「公開ページのレート制限」）。

| 層 | キー | 上限 | 目的 |
| --- | --- | --- | --- |
| Next.js `proxy.ts` | **実クライアント IP** | 60 req/分 | 連打の抑止。実 IP で絞れるのはここだけ |
| Spring Boot | **グローバル（総量）** | 300 req/分 | Vercel からの総量を守る最後の防波堤 |
| Next.js ログイン | 実クライアント IP | 5 回/15 分 | パスワード総当たりの抑止（T-02） |
| Spring Boot ログイン | **グローバル（総量）** | 5 回/15 分 | 内部キーを持つ攻撃者が直接叩く場合（T-02） |

**Spring Boot 側を IP で絞らない。** ここから見た送信元は Vercel の egress IP に
集約されるため、IP 単位に絞ると攻撃者ではなく**全閲覧者がまとめて絞られる**。
そのぶん**発動すれば閲覧者全体に影響が出る**ので、値は広く取る。

**ログインも同じ理由で IP では分けられない。** 実装のキーは
`HttpServletRequest#getRemoteAddr()` だが、`server.forward-headers-strategy` を
設定していないため、Fly.io の proxy 越しでは**全リクエストが同じ値に集約される**。
事実上グローバルな 5 回/15 分である。

**それで足りるのは `/internal/auth` に管理キーが要るから。**
`SecurityConfig` が `hasAuthority(ROLE_ADMIN)` を課しており、キーを持たない相手は
レート制限まで届かない（`403`）。この層が守るのは
「**内部キーは漏れたが管理者パスワードは漏れていない**」場合だけで、
そこを叩ける相手を IP 単位に分ける意味がない。

**値の根拠。** ISR の再検証は 5 分間隔で、表示できる年月は
**サービス開始月（`2026-01`）から現在（JST）の月 + 24 か月まで**
（[requirements.md](requirements.md) FR-05 /
[ADR-0014](adr/0014-bounded-calendar-range.md)）。
**下限が固定で上限が現在基準なので、この幅は毎月 1 か月ずつ増える。**

- **2026-09 時点で 33 か月**（`2026-01` 〜 `2028-09`）
- 全ページが同時に期限切れになっても
  33 ページ × 2 リクエスト ÷ 5 分 ≒ **13 回/分**が最悪値。300 はその約 23 倍
- 最悪値が 300 に届くのは幅が 750 か月になったときで、**60 年以上先**。
  この見積もりが先に壊れるとしたら、再検証の間隔を縮めたときか、
  年月の範囲を広げたときである

公開ページ側の 60 req/分は、通常の閲覧が 1 分に数回であることに対する余裕。

**キーの検証を通ったリクエストだけ数える。** キーの無いものはどのみち `403` で
DB に到達しないため、数えると**不正な通信が正規の枠を食い潰せてしまう**。

### 4.3 レート制限で守れないもの

**Vercel の枠を守り切るものではない。** 弾いたリクエストも Vercel の関数呼び出しを
1 回消費する。効果は「**ページレンダリング・バックエンド往復・ISR 再生成を避けて
リクエスト単価を下げる**」ことであり、ゼロにはならない。

**管理者自身が締め出される。** ログインのキーがグローバルなので、
パスワードを 5 回間違えれば 15 分は正しいパスワードでも通らない。
単一管理者の運用ではこれは総当たり対策の意図した挙動だが、
**内部キーが漏れていれば第三者にも引き起こせる**。
締め出しは 15 分で自然に解け、カウンタはプロセスの再起動でも消える
（`LoginAttemptLimiter`）。公開カレンダーは影響を受けない（NFR-02）。

**インスタンスをまたぐと共有されない。** カウンタはプロセス内のメモリにあり、
Vercel で実行環境が変われば数え直しになる。外部ストア（Redis 等）を使えば正確になるが、
新規依存と従量課金、そして障害点が 1 つ増える。

これを許容できるのは、**T-04 の主防御が別にあるため**。年月の受理範囲が有限で
（ADR-0014）、キャッシュミスを作れる URL は**その月数ぶん**（2026-09 時点で 33 個）に
限られる。
レート制限はその上に重ねる 1 枚であって、単独で成立させる設計ではない。
**キャッシュや範囲の限定を外す変更を入れるなら、ここも設計し直す。**

## 6. インシデント対応

### 6.1 X API トークンの漏洩

1. **X Developer Portal でトークンを即座に無効化する**
2. 新しいトークンを発行し、`fly secrets set` で差し替える
3. 課金額を確認する。想定外の消費があれば X のサポートへ連絡する
4. 漏洩経路を特定する（コミット履歴、ログ、設定）
5. **履歴からの削除だけで済ませない。** 一度公開されたトークンは無効化する

### 6.2 管理者パスワード・管理 API キーの漏洩

1. パスワードを変更し、BCrypt ハッシュを差し替えてデプロイする
2. `INTERNAL_ADMIN_API_KEY` と `SESSION_SECRET` を再生成する
   （鍵を変えると発行済みセッションが無効になる。本書「受容するリスク」の制約への対処にもなる）
3. **公開データが改ざんされていないか点検する**。
   `updatedAt` が想定外に新しい行、身に覚えのない登録を確認する
4. 誤情報が公開されていた場合は削除し、必要ならサイト全体を止める（本書「誤った出演情報の公開が判明した場合」）

### 6.3 誤った出演情報の公開が判明した場合

1. 該当する出演情報を削除する（FR-23）
2. 原因を確認する（抽出ミス／情報源の誤り／乗っ取り）
3. 抽出ミスであれば `docs/x-post-sample/` にその投稿を追加し、テストを増やす
4. 広範囲に及ぶ場合は `SITE_DISABLED=true` でサイト全体を止めてから修正する
   （[architecture.md](architecture.md)「サイト全体の停止」。LR-05）。
   停止中も `/admin` は使えるため、止めたまま個別削除を進められる

### 6.5 削除要請・問い合わせを受けた場合

窓口はサイト専用のメールアドレス（[ADR-0017](adr/0017-contact-channel.md)）。
**アドレスの正本は `frontend/lib/contact.ts`** で、ここには書かない。

1. **受領をまず返信する。判断より先に返す。** 対応中であることが伝わらないと、
   要請者は次の手段（ホスティング事業者やプラットフォームへの通報）に進む
2. 対象を特定する（日付・イベント名・該当ページの URL）。分からなければ聞き返す
3. 範囲が限定的なら該当の出演情報を削除する（FR-23）
4. 広範囲、または要請の趣旨がサイト全体に及ぶ場合は `SITE_DISABLED=true` で
   止めてから対応する（本書「誤った出演情報の公開が判明した場合」と同じ手順）。**停止中も `/admin` は使えるため、
   止めたまま個別削除を進められる。** 停止ページには窓口が残る
5. 対応が終わったら結果を返信する
6. 抽出由来の誤りであれば、本書「誤った出演情報の公開が判明した場合」の 3 も併せて行う

**窓口は個人の受信箱へ転送している。転送が切れると気づけないまま要請を放置することになる**
（本書「定期的な確認」）。

### 6.4 情報源アカウントの乗っ取りが判明した場合

1. **取り込みジョブを停止する**（環境変数でジョブを無効化できるようにしておく）
2. 乗っ取り期間中に登録された出演情報を洗い出して削除する
3. 公式の復旧を待ってから取り込みを再開する

## 8. 受容するリスク

個人開発として、次は**対策せず受容する**。判断を明示しておき、
状況が変わったら見直す。

| リスク | 受容する理由 |
| --- | --- |
| 発行済みセッションの即時失効ができない | 単一管理者で被害範囲が限定的。有効期限 8 時間で抑える。緊急時は `SESSION_SECRET` の再生成で全セッションを無効化できる |
| Spring Boot がインターネットに露出する | Vercel の送信 IP が固定されないため IP 制限が使えない。API キーで補う |
| ホスティング事業者（Vercel / Fly.io / Neon）の侵害 | 個人で対策不能。事業者の対策に依存する |
| DDoS | Vercel の標準的な保護に依存する。専用の対策を導入しない |
| 情報源アカウントの乗っ取り | 完全な防止は不可能。検知と復旧で対応する（T-05） |
| バックアップが Neon 任せ | 現状は Neon の自動バックアップのみ。本書「未決定事項」の未決定事項 |
