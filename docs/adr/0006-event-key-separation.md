# ADR-0006: イベント名を表示用と照合用に分離する

- status: 承認済み
- 日付: 2026-08-28

## 背景

[ADR-0004](0004-fill-blanks-only.md) により、同一イベントを判定する必要が生じた。
イベント名には表記ゆれがある（括弧の種類、全角・半角、半角カナ）ため
正規化が要るが、**正規化した文字列を表示に使うと元の告知と違う名前が
カレンダーに並ぶ**という問題があった。

## 決定

**2 つの列に分ける。**

| 列 | 用途 | 値 |
| --- | --- | --- |
| `event_name` | 画面表示 | 告知の原文（`『ORANGE CHEER』`） |
| `event_key` | 同一判定 | 正規化後（`orangecheer`） |

`UNIQUE (appearance_date, event_key)` を張る。
（一意キーはのちに出演開始時刻を加えて 3 列へ拡張した。[ADR-0012](0012-multi-slot-uniqueness.md)）

正規化は **NFKC → 小文字化 → 英数字・日本語文字以外を除去**。

## 理由

- **`UNIQUE` を `event_key` 側に置くことで、アプリの照合ロジックと
  DB の制約が同じキーで判定する。** `event_name` に制約を張ると、
  表記ゆれをアプリが吸収しても DB が別物として通し、二重登録を防げない
- NFKC 正規化は必須。実サンプルのイベント名に**半角カナ**（`ﾆｷﾌﾟﾚ`）が含まれ、
  全角で再告知された場合に別物と判定されてしまう

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| 比較の直前にだけ正規化する（列を持たない） | DB の `UNIQUE` が原文で判定するため制約が実質機能しない |
| 正規化した値だけを保持する | 表示が元の告知と変わる |
| **先頭数文字に切り詰めたキーを使う** | 実データで破綻を確認（下記） |

**切り詰め案の検証結果。** 「英数字のみ 5 文字」で試したところ、

- `#ﾆｷﾌﾟﾚ『カンシャサイ。-秋-』` → 英数字がなく**空文字**になる
- `LONELY KIDS` と `LONELY NIGHT` が両方 `lonel` で**衝突**
- `ORANGE CHEER` と `ORANGE PARTY` が両方 `orang` で**衝突**

同じ日に掛け持ち出演した別イベントを同一とみなし、
空欄補完で**片方がカレンダーから消える**。誤情報の公開に直結するため採用しない。

## 結果

- `event_key` は**アプリケーション層で生成する**。NFKC を含むため
  PostgreSQL の生成列では環境依存になりやすい
- `event_name` を変更する経路（自動登録・手動登録・編集）すべてで再計算が必要。
  サービス層に単一の生成メソッドを置く
- 公開 API は `event_key` を返さない。内部の実装詳細であり画面に出す値ではない
- 正規化は表記の揺れしか吸収できない。略称と正式名称の使い分けは別イベントになる。
  取りこぼしの保険として手動削除（FR-23）を残す
