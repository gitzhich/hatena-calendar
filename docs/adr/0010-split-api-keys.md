# ADR-0010: 内部 API キーを公開用と管理用に分離する

- status: 承認済み
- 日付: 2026-08-28

## 背景

[ADR-0008](0008-nextjs-bff.md) の BFF 構成では、Next.js から Spring Boot への
呼び出しを共有シークレット（内部 API キー）で保護する。
Vercel の送信 IP が固定されないため IP 制限が使えず、キーが唯一の防御線になる。

**当初は 1 種類のキーで設計していた。** API 設計を詰める段階で、
これでは公開データの取得キーが漏れただけで管理操作まで通ることに気づいた。

## 決定

**キーを 2 種類に分ける。**

| ヘッダ | 環境変数 | 通せる範囲 |
| --- | --- | --- |
| `X-Api-Key` | `INTERNAL_API_KEY` | 公開 API のみ |
| `X-Admin-Api-Key` | `INTERNAL_ADMIN_API_KEY` | 管理 API・内部 API |

Next.js は**管理者セッション Cookie の検証に成功した場合にのみ**管理キーを使う。

## 理由

- 公開データの取得キーは**全ページのレンダリングで使われ、露出機会が多い**。
  ログ、エラー、設定ミスなど漏洩の経路が管理キーより広い
- 1 種類だと、その広い露出面が**そのまま管理操作の権限になる**。
  リスクの大きさが釣り合わない

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| 単一キー | 公開側の露出リスクが管理操作へ波及する |
| mTLS | 個人開発には運用コストが過剰。証明書の更新管理が増える |

## 結果

- 公開ページのレンダリングで管理キーを読み込まない実装制約が生まれた
- 環境変数が 1 つ増えた（Next.js 側・Spring Boot 側の双方）
- キーの比較は**固定時間比較**で行う。文字列の `equals` を使わない
- 漏洩時は両方を再生成する。`SESSION_SECRET` も併せて再生成すると
  発行済みセッションを無効化できる
