# ADR-0022: 会場を正規化し、地域と Google の place_id を持たせる

- status: 承認済み
- 日付: 2026-09-08（2026-09-12 に区名の扱いを決着）

## 背景

会場は `appearance.venue_name` に**自由記述の 1 列**として入っている。
公式の告知が `{地名}・{会場名}` の形で書くため、抽出もその形のまま保存している
（[x-integration.md](../x-integration.md)「会場」）。

ここに 2 つの要望が出た。

1. **会場から地図を開けるようにしたい。** 公式の投稿に地図リンクは無いので、こちらで用意する
2. **カレンダーのチップを会場の地方で色分けしたい。** 遠征かどうかが一目で分かる

どちらも「会場文字列から地域を判定する」「会場に外部の識別子を紐づける」という、
**いまのデータモデルが持っていない情報**を必要とする。

### 実データで分かった制約

`docs/x-post-sample/` の実投稿から会場表記を全件取り出した結果、
素朴な実装が壊れる形が揃っていた。

| 表記 | 何が問題か |
| --- | --- |
| `金沢・REDSUN` | **`・` の前は都道府県とは限らない。** 金沢は市名 |
| `韓国・SETi LIVE HALL` | **国内とも限らない** |
| `千葉・草ぶえの丘(千葉 佐倉) / Orange Shelter` | 単一会場だが `/` と括弧を含む |
| `愛知・大須RADHALL` / `愛知・大須RAD HALL` | **同じ会場が別表記で現れる** |
| （NULL） | 複数会場の告知は空欄で登録する（[ADR-0021](0021-register-appearances-without-timetable.md)） |

**表記ゆれと判定失敗は避けられない。** 自動判定だけに頼る設計にはできず、
**人が 1 か所直せば全体に効く**構造が要る。

## 決定

### 1. `venue` テーブルを足して会場を正規化する

正規化したキーで会場を 1 行にまとめ、そこに地域と `place_id` を持たせる。
`appearance` からは `venue_id` で参照する。

**`appearance.venue_name` は残す。** 原文の表記は出典に紐づく事実であり、
`venue` が持つのは代表表記である。`大須RADHALL` と `大須RAD HALL` は
同じ会場を指すが、**どちらの投稿がどう書いたかは変えてはいけない**。

キーの作り方は既存の `event_key`（[data-model.md](../data-model.md)「正規化ルール」）に倣う。
同じ流儀を 2 つ持つと片方だけ直す事故が起きるため、規則を揃える。

### 2. 地域は 8 地方 + 海外 + 不明の 10 区分にし、バックエンドが判定する

```
HOKKAIDO / TOHOKU / KANTO / CHUBU / KINKI / CHUGOKU / SHIKOKU / KYUSHU
OVERSEAS   海外
UNKNOWN    判定できない・会場が空欄
```

**判定は表示ではなくデータの分類である。** 47 都道府県の対応表と主要都市の別名
（金沢 → 石川 → 中部）を持つ知識であり、**将来のモバイル（NFR-07）でもう一度書きたくない**。
公開 API が `region` を返す形にする。

**色の割り当てはクライアントに置く。** どの地方を何色にするかは見た目の決定で、
バックエンドが知る必要が無い。

### 3. `place_id` を保存し、地図リンクは Maps URL で作る

```
https://www.google.com/maps/search/?api=1&query={会場名}&query_place_id={place_id}
```

Google 自身がこの組み合わせを推奨している——
「**Place ID をできる限り使い、宛先を確実に指定する**」。
名前だけの検索は同名の別施設に当たりうる。

`place_id` の解決には **Places API の Text Search (IDs Only)** を使う。
Google が「**Place ID を得るためのゼロコストな方法**」と明記しており、
月次の無料枠すら消費しない。

**呼び出しは会場ごとに 1 回だけ。** 閲覧のたびでも、取り込みのたびでもない。
実サンプルに出る会場は 15 種類で、生涯でも 100 種類に届かない見込み。

**`place_id` は無期限に保存してよい。** Google のポリシーが
キャッシュ制限の**例外**として明記している（他のフィールドは 30 日制限、
名前・評価・写真は保存不可）。

### 4. Places のデータは `place_id` 以外持たない

名前・住所・評価・写真を取得しない。会場名は**X の投稿から得た我々のデータ**を使う。

これにより**帰属表示（"Powered by Google"）が不要**になる。
帰属が要るのは Places のコンテンツを表示する場合であり、
`place_id` を保存して Google マップへ送るだけなら該当しない。

### 5. 会場の引き当ては登録時、place_id の解決は 1 日 1 回の定期実行

**2 つを分ける。** 前者は DB の中だけで完結し、後者は外部 API を呼ぶ。

| 何を | いつ | なぜ |
| --- | --- | --- |
| `venue` の引き当て・作成と `venue_id` の設定 | **出演情報の登録時**（自動・手動とも） | 承認フローが無く登録が即公開されるため、地域（＝色）が遅れて付くのは具合が悪い。外部 API を呼ばないので取り込みのトランザクションに入れて安全 |
| `place_id` の解決 | **1 日 1 回の定期実行** | Places API を取り込みのトランザクションから切り離すため |

**取り込みのトランザクションから Places API を呼ばない。**
X API の取り込みが Google 側の障害で失敗するのは筋が悪く、
`consecutive_failure_count` を無関係な理由で進めてしまう
（[x-integration.md](../x-integration.md)「エラーハンドリング」/ FR-43）。
逆も同じで、**取り込みが打ち切られていても会場の解決は走る**。
X API の健康状態と Google の可用性は無関係である。

#### 頻度を 1 日 1 回にした理由

**Neon の起動回数が無料枠を決める。** 最終クエリから 5 分でサスペンドするため、
ジョブが DB に触るたびに最低 5 分は起動したままになる
（[architecture.md](../architecture.md)「運用コストの試算」）。

| 間隔 | 月間の起床 | 0.25 CU 換算 |
| --- | --- | --- |
| 1 時間 | 約 60 時間 | **約 15 CU-hours** |
| **1 日（採用）** | 約 2.5 時間 | **約 0.6 CU-hours** |

取り込みが既に約 31 CU-hours を使い、閲覧・再検証・管理操作に残るのは約 69。
**毎時にすると、その残りから 2 割強を恒久的に削る**ことになる。

**毎時である必要が無い。** 新しい会場が現れるのは数週間に 1 度で、
しかも**未解決の間も地図リンクは名前検索で機能する**。
遅れて困るものが 1 つも無い。

**起動の 5 分後に 1 回走らせる。** デプロイ直後に初期投入が動き、
待たされない（本書「既存データの初期投入」）。

#### 暴走と無駄叩きを防ぐ

- **1 回の実行で解決するのは上限 N 件**。API の異常時に延々と叩かない
- **前回の試行から一定期間（7 日）空いたものだけ再試行する。**
  見つからなくても `place_id_checked_at` を更新する。
  記録しないと、Google に存在しない会場を毎日叩き続ける
- **「見つからない」と「到達できない」を分ける。** 前者は正常な結果なので記録する。
  後者は**試行として記録せず、その回はそこで打ち切る**。混ぜると、Google の障害が
  「存在しない会場」として記録され、**障害が明けても再試行が 7 日先へ飛ぶ**。
  打ち切っても翌日また走るので、失うものは無い
- **再試行しない（HTTP のレベルで）。** 取り込みが 429 / 5xx を指数バックオフで
  再試行するのは、逃した投稿が次の実行までカレンダーに載らないため。
  こちらは未解決の間も名前検索の地図リンクが機能するので、その場で粘る理由が無い

### 6. 手作業を運用の前提にしない

**定常運用に人の操作を必要としない。** 会場の引き当ても `place_id` の解決も
自動で進み、管理者が触るのは**自動判定が外れたときの訂正だけ**である。

**自動判定は必ず外れる。** 金沢のような市名、韓国のような国名、
未知の会場名がそれに当たる。**誤った地図リンクは、リンクが無いより悪い**——
ファンが違う場所へ向かう。

`venue` は 1 会場 1 行なので、**1 行直せば過去の全出演に効く**。
管理画面に会場の一覧と編集を置く。**訂正した行は自動処理が上書きしない**
（`manually_edited`）。

**未解決の会場が残り続けても実害は小さい。** 名前検索の地図リンクに落ちるだけで、
画面は壊れない。したがって能動的な警告は出さず、会場の一覧で見えれば足りる
（警告を増やすと、本当に見るべき取り込みの警告が埋もれる。NFR-09）。

### 7. 会場が未定でも地域は持つ

**会場が並ぶ告知は会場を空欄で登録する**（[x-integration.md](../x-integration.md)「会場」）。
このとき地域まで失われると、**東京の公演なのにカレンダーの色が付かない**。
実サンプル 1.txt / 22.txt / 28.txt がこの型で、本番にも既に存在する。

「会場は未定だが東京であることは分かっている」を表せるようにする。

```
appearance
  venue_name = NULL      会場は未定（空欄補完が効く状態を保つ）
  area_name  = 東京      引き当ての入力。地域そのものではない
  venue_id   = 57

venue
  id=57  venue_key=東京  display_name=東京  region=KANTO
  place_id=NULL  area_only=true
```

**`region` の置き場所は `venue` のまま 1 か所。** `area_name` は `venue_name` と
同じ「引き当ての入力」であって、地域ではない。読み出しは `venue.region` を見るだけで
分岐が要らず、管理者が `東京` の行を直せば**その地域の全出演情報に効く**。

**`venue_name` に地名を入れてはいけない。** 一見それが最小の変更だが、値が入ると
空欄補完が上書きしないため（[ADR-0004](0004-fill-blanks-only.md)）、
**タイムテーブル解禁が来ても実際の会場に直らない**。空欄のままでなければならない。

**地図リンクは出さない。** `area_only` の行は `place_id` の解決対象から外し、
未解決時のフォールバック（名前検索）も行わない。`東京` で地図を検索させると
東京駅のような無関係な場所を指す。**誤った地図リンクはリンクが無いより悪い**
（[security.md](../security.md) T-08）。

**会場が確定したら `venue_id` が張り替わる。** 後続のタイムテーブル解禁が
`venue_name` を埋めると、引き当てが実会場を指す。`area_name` は原文に基づく事実として
残すが、**`venue_name` があるときはそちらが勝つ**。

**会場が確定している告知には `area_name` を入れない。** 地域は `venue` から引けるので
不要であり、2 つ持てば食い違う余地を作るだけである。

### 8. 地域はチップの色で示し、凡例と絞り込みを添える

**カレンダーのチップの色を地域にする。** それまでの「イベント名のハッシュで色を割り当てる
（意味は持たない）」をやめる。**同じイベントなら同じ色**という手がかりは失われる
（実データで複数日にまたがるイベントが 10 件ある）。

**10 区分を均等に扱わない。** 実データの分布が偏っているため。

| 区分 | 地域 | 扱い |
| --- | --- | --- |
| 強調 | 関東 / 中部 / 近畿 / 海外 | 色相をはっきり分け、混同しやすい組（緑と橙、青と紫）は明度でも離す |
| 低頻度 | 北海道 / 東北 / 中国 / 四国 / 九州 | 互いに近い色でよい |
| 無彩色 | 不明（会場が空欄のものを含む） | **色相を持たせない。** 判定できないものを特定の地域として見せない |

**凡例と絞り込みを同一物にする。** カレンダーの上に、その月に出演がある地域だけを
チップと同じ塗りのトグルで並べる。押すとその地域だけに絞り、もう一度押すと解除する。

- 出るのは 10 個ではなく **4〜5 個**（実データの全月がこの範囲）
- 件数を添える。**色を見なくても月の内訳が読める**
- 選択状態は `outline` と `aria-pressed` で示す。色でも不透明度でも示さない

**塗りは小さく、タップ対象は透明な余白で 44px を確保する。**

```
┌──────────────┐ ← button（44px。ここ全部が押せる）
│  ╭────────╮  │
│  │ 関東 13 │  │ ← 塗りは 20px
│  ╰────────╯  │
└──────────────┘
```

[requirements.md](../requirements.md) NFR-06 が求めるのは**押せる領域の大きさ**であって
塗りの大きさではない。**`border` ではなく `outline` で選択状態を出す。** `border` は
箱を膨らませ、折り返しの計算を狂わせる。

**透明な余白は前後の margin に食い込ませる**（負のマージン）。食い込ませないと
上下 12px ずつが前後の `mb-4` と足し算され、**見た目の間隔が 28px になって間延びする**。
食い込ませても、上は月見出し行との間に 4px 残るので**タップ領域は重ならず**、
下の曜日見出しは押せないので影響が無い。**負のマージンだけを見ると浮いて見えるが、
外すと間延びが戻る。**

#### 絞り込みはページ全体に効かせる

**選択は日付セルのチップ・日別シート・ページ下部の出演一覧すべてに効く。**

当初はカレンダーだけだった。`selectedRegion` を `DayGrid` の state に置いたためで、
出演一覧は `CalendarPage` が `Calendar` の**兄弟**として描く Server Component だから
選択が届かない。**カレンダーが 1 件に絞られているのに、下には全件が並ぶ。**

状態を両者の共通の親（`RegionScope`）へ持ち上げ、Context で配る。カードはサーバで
描いたまま `children` で渡し、一致しないものをクライアント側の `RegionFiltered` が
出さない。**ページ全体を `"use client"` にしない**——すると ISR が無効になり、
無料枠の枯渇による可用性攻撃への主防御が壊れる
（[ADR-0016](0016-static-csp-public-nonce-admin.md) / [security.md](../security.md) T-04）。

**絞り込みですべて隠れたところでは、無いとは言わず隠していると出す。** 日付セル・
日別シート・出演一覧の 3 か所で同じ扱いにする。「出演なし」と出すと、
**出演が無い日と、絞り込みで消えた日が同じ見た目になる**。

#### 2 度作り直している

**1 度目: トグルが大きすぎた。** 塗りを `text-sm px-3 border-2` にしたところ、
チップ 1 個が約 73px になり、6 個（「すべて」を含む）で幅 360px では **2 行・約 96px**
を占めた。カレンダー本体は 6 週で約 280px なので、その 3 分の 1 である。

**2 度目: 分離したらアンバランスになった。** 凡例を押せなくして 22px に落とし、
絞り込みを `<select>` にして横に置いた。**縦幅は 66px まで減ったが、幅 120px・
高さ 44px の `<select>` と高さ 20px のピルが並ぶ構図の収まりが悪く、見た目が悪化した。**

**分けたことではなく、塗りの大きさが問題だった。** 塗りを小さいままトグルに戻すと
1 行・44px に収まり、見た目も凡例の行のままになる。

| | 高さ（幅 360px） |
| --- | --- |
| 1 度目（大きいトグル） | 96px（2 行） |
| 2 度目（分離） | 66px |
| **現行（小さいトグル）** | **44px（1 行）** |

#### 寸法の測り方

**画像の幅をビューポート幅と思い込まない。** 1 度目の数字（「113px」「3 行・148px」）は
スクリーンショットの画像幅をそのまま CSS 幅と仮定して出したもので、**誤りだった**。

幅の違う 2 枚があれば連立で解ける。内容幅は「端末幅 − 32px」（`max-w-2xl px-4`）。

- 幅 360px（内容 328px）: 要素 4 個が載り、5 個目が折り返した
- 幅 412px（内容 380px）: 5 個が載り、折り返さなかった

差から `ピル + gap = 52px`、`gap` が 8px なので **ピル = 44px**。
これで両方の式が内容幅ちょうどに一致する。

#### 「すべて」のチップを作らない

トグル 1 個は 48px 程度なので、5 個なら `48×5 + 8×4 = 272px` で幅 360px に
56px の余裕を残して収まる。**「すべて」を足すと 6 個で 328px ちょうど**になり、
見積もりが少しでも甘いと折り返して 88px になる。

解除は「選択中をもう一度押す」で足りる。失うのは月の合計だけで、
それは凡例の件数を足せば分かる。

#### `<select>` にしない

`<option>` の背景色は iOS Safari の native picker で無視され、閉じている
`<select>` は選択中の 1 件しか見えない。**凡例を兼ねられない。**
分離すればこの制約は消えるが、上記のとおり見た目が成立しなかった。

**横スクロールで 1 行に収めない。** 隠れているものに気づけないうえ、
見た目としても採らない。

**凡例を色見本の四角にしない。** 地域色と背景の比は **1.17〜2.14:1** しかなく、
四角だけでは輪郭が背景に埋もれる（非テキストの図形は 3:1 が目安）。
チップと同じ「塗り + 文字」にすれば文字のコントラストで見え、
**凡例とカレンダーのチップが同じ見た目になる**という本来の目的にも合う。

**絞り込みの状態を URL に載せない。** 公開ページは年月ごとに ISR でキャッシュされており、
受け付ける年月の範囲を有限にしてキャッシュミスの無制限な生成を防いでいる
（[ADR-0014](0014-bounded-calendar-range.md) / [security.md](../security.md) T-04）。
`?region=` を足すと**キャッシュの種類が地域の数だけ増え**、この防御が薄くなる。
1 か月分のデータは既に全件取得しているので、**絞り込みはクライアント側で完結する**。

#### WCAG 2.2 達成基準 1.4.1 について

**満たすもの。** 地域という情報は色を知覚しなくても得られる——トグルの名前と件数、
出演一覧と詳細の会場名（`東京・渋谷DESEO` の形）、地域ラベル。

**残るもの。** **カレンダーを一瞥して、隣の日と地方が違うことを色抜きで判別する
手段は無い。** チップは幅 43.4px・文字 9px で、記号も文字も入らない
（[requirements.md](../requirements.md) NFR-06）。地方名 1 文字は
**中部と中国がどちらも「中」**になり成立しない。

**この残差を承知のうえで採る。** 実データでは 1 日に複数の地域が並ぶ日が
72 日中 1 日しかなく、色が区別しているのは「日と日」である。絞り込みで 1 つ選べば
その地域だけが残るので、**色に頼らず日を特定できる**。

#### 配色の検証

`scripts/check-contrast.py` が `frontend/app/globals.css` のトークンを読み、
**全ペアのコントラスト比を検査して CI で落とす**。地域色でペアが 20 増えるため、
手計算では追随できない。

## 選ばなかった案

**検索 URL だけを組み立てる（`place_id` を持たない）。**
DB もキーも要らず最も簡単だが、`大須RAD HALL` のような表記ゆれや
`千葉・草ぶえの丘(千葉 佐倉) / Orange Shelter` のような複合表記で外す。
**費用が同じ（どちらも $0）である以上、精度を捨てる理由が無い。**
ただし `place_id` が未解決の間はこの形にフォールバックする。

**`appearance` に `venue_region` と `venue_place_id` の列を足す。**
テーブルを増やさずに済むが、**同じ会場が現れるたびに同じ値が複製される**。
表記ゆれの補正も、`place_id` の修正も、行数ぶん繰り返すことになる。
「1 か所直せば全体に効く」という要件を満たせない。

**Places API を使わず、管理者が地図 URL を手で貼る。**
精度は最も高いが、**会場が出るたびに手作業が要る**。
IDs Only が無料である以上、まず自動で埋めて例外だけ直すほうが手数が少ない。

**取り込みと同じスケジューラのティックに相乗りする。**
Neon は取り込みのために既に起きているので、追加の CU-hours は実質ゼロになる。
それでも採らなかった理由は 2 つ。`ingestion.enabled=false` が
`IngestionScheduler` のビーンごと落とすため、**取り込みを止めると会場の解決も
止まる**（ローカル開発では常に止めている）。加えて、切り離したはずの 2 つが
スケジュールで再び結び付く。**1 日 1 回なら 0.6 CU-hours** で、
相乗りの利点が小さい。

**`appearance` に地域そのもの（`region`）を持たせる。**
列が 1 つで済むが、**地域の出所が `venue.region` と 2 つになる**。読み出しに分岐が要り、
管理者の訂正は行ごとになって「1 か所直せば全体に効く」が成り立たない。
本書が既に却下した「`appearance` に `venue_region` と `venue_place_id` の列を足す」と
同じ欠点である。

**判定をフロントエンドに置く。**
バックエンドのデプロイが要らなくなるが、47 都道府県の対応表と別名の知識を
**モバイル追加時にもう一度書く**ことになる。地域の分類は表示ではなくデータである。

## 既存データの初期投入

**すでに運用中**で、`venue_name` を持つ出演情報が本番に存在する
（初回バックフィルで 76 件、以後も増えている。[requirements.md](../requirements.md)
「リリース判定基準（Definition of Done）」）。これらに `venue_id` を付ける必要がある。

### 移行を SQL で書かない

マイグレーションが作るのは**テーブルと列だけ**にする。
`venue_key` の正規化と地域の判定は**アプリ側のロジック**であり、
**SQL に書き直すと実装が 2 つになる**。片方だけ直す事故が必ず起きる。

### 通常運用と同じ経路で埋める

定期実行に、`place_id` の解決とは別の段を持たせる。

```
段 1  venue_id が未設定で venue_name がある出演情報を拾い、
      venue を引き当て（無ければ作成）して venue_id を設定する    ← DB のみ
段 2  place_id が未解決の会場を上限 N 件だけ解決する              ← Places API
```

**段 1 が初期投入そのものになる。** 専用の移行コードを書かない。
デプロイの 5 分後に走り、**残りが無くなるまで繰り返す**ので 1 回の実行で片付く。

段 1 は初期投入が済んだあとも**取りこぼしの保険**として残す。
登録時の引き当てに漏れがあっても、翌日には埋まる。

### 満たすべき性質

- **冪等。** 途中で落ちても、次回が続きから拾う。二重に作らない
  （`venue_key` の `UNIQUE` が最後の砦）
- **`venue_name` を書き換えない。** 原文は出典に紐づく事実である
- **段 1 の失敗が段 2 を止めない。** 逆も同じ
- **件数の区切りはトランザクションの大きさのためで、1 日あたりの上限ではない。**
  数百件を 1 トランザクションで抱えず、区切りながら残りが無くなるまで進む
- **拾う条件と紐づける条件を一致させる。** 空白だけの会場名は「会場なし」として
  紐づけないので、拾う側でも除く。ずれると**同じ行を永久に返し続ける**

### 実測（ローカル、2026-09-09）

本番から取った 79 件を含む 93 件に対して実行した結果。

| | |
| --- | --- |
| 紐づけた出演情報 | **91 件**（会場が空欄の 2 件は対象外）。1 回の実行で完了 |
| できた会場 | **60 行**（相異なる表記は 61。`大須RADHALL` と `大須RAD HALL` が 1 行に寄った） |
| 地域を判定できた会場 | **58 / 60** |
| 判定できなかったもの | `恵比寿LIQUIDROOM` と `新宿LOFT` |

**判定できなかった 2 件は、どちらも地名の接頭辞が無い表記。**
実データの大半は `東京・渋谷DESEO` の形だが、**接頭辞を欠く表記も実在する**。

**区名・地区名（恵比寿・新宿・渋谷…）は表に足さない。** 本番でも該当は
56 件中の同じ 2 件だけで、管理画面から手で直すほうが速い
（[api.md](../api.md)「会場の一覧と編集」）。どこまで足すかに線引きが無く、
**足した表が誤っていると色が黙って間違う**。判定できずに `UNKNOWN` として出るほうが、
誤った地域を自信を持って出すより安全である（同じ理由で `place_id` も推測で入れない）。

### 初期投入の確認

デプロイ後、**管理画面の会場一覧で確認できる**（[api.md](../api.md)「会場の一覧と編集」）。

- 相異なる会場が並び、`appearanceCount` の合計が `venue_name` を持つ出演情報の件数と一致する
- `region` が `UNKNOWN` の行が**判定できなかった会場**。金沢のような市名がここに出る
- `place_id` が `null` の行が**まだ解決していない会場**

**`UNKNOWN` が残っていても壊れていない。** 判定できないものを推測で寄せるより、
分からないと表示して人が直すほうが安全である。

## 影響

- **新しいシークレットが 1 つ増える**（Google Maps API キー）。[security.md](../security.md) T-08
- **既存の「会場が空欄」の行は自動では救えない。** `ingested_post` は本文を保持しない
  （LR-02）ため、投稿を読み直して `area_name` を埋めることができない。
  本機能より前に登録された行は、管理者が点検一覧から手で入れる
- **外部依存が 2 つ目になる。** Places が落ちても、既に解決済みの `place_id` で
  地図リンクは出続ける。未解決の会場は検索 URL に落ちる
- **チップの色が意味を持つようになる。** いままで `chip-color.ts` は
  「意味は持たない（NFR-08）」と明記していた。この前提が変わる（次節）
- 色の区分が 6 から 10 に増える。**配色とコントラストの再検証が要る**

## 未決定: 12 か月を超えた place_id をどう扱うか

**キャッシュしてよいことと、古びないことは別である。** Google は `place_id` を
キャッシュ制限の例外として無期限の保存を認める一方で、**12 か月を超えたものは
リフレッシュすることを推奨**している。施設の統廃合などで ID が変わりうるため。

本書「`place_id` を保存し、地図リンクは Maps URL で作る」の
「無期限に保存してよい」は**キャッシュの許諾の話であって、鮮度の話ではない**。
混同しないこと。

リフレッシュは **Place Details に ID だけを指定すれば無料**で行える。
Text Search (IDs Only) と同じく、識別子しか受け取らない呼び方が無料になっている。

**いまは実装していない。** 運用開始から 12 か月経つまで実害が出ないため、
そのときの分布を見てから決める。決める際の論点は 3 つ。

- **古い `place_id` が無効になったとき、地図リンクがどう振る舞うか。**
  Maps URL は `query`（会場名）を併記する形なので名前検索に落ちると見込まれるが、
  **未検証**。もし誤った場所を指すなら実害は大きい（[security.md](../security.md) T-08）
- **リフレッシュの経路。** 定期実行の段 2 に「12 か月を超えた行」を足すのが自然だが、
  呼ぶのが Text Search ではなく Place Details になる
- **割り当ての戻し忘れ。** 運用では `GetPlaceRequest` を 0 にしているため、
  入れるときは上限も戻す（[runbook-deploy.md](../runbook-deploy.md)「割り当てで上限を縛る」）
