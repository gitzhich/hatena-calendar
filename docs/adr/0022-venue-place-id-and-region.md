# ADR-0022: 会場を正規化し、地域と Google の place_id を持たせる

- status: 承認済み
- 日付: 2026-09-08

## 背景

会場は `appearance.venue_name` に**自由記述の 1 列**として入っている。
公式の告知が `{地名}・{会場名}` の形で書くため、抽出もその形のまま保存している
（[x-integration.md](../x-integration.md)「会場」）。

ここに 2 つの要望が出た。

1. **会場から地図を開けるようにしたい。** 公式の投稿に地図リンクは無いので、こちらで用意する
2. **カレンダーのチップを会場の地方で色分けしたい。** 遠征かどうかが一目で分かる

どちらも「会場文字列から地域を判定する」「会場に外部の識別子を紐づける」という、
**いまのデータモデルが持っていない情報**を必要とする。

### 実データで分かった制約

`docs/x-post-sample/` の実投稿から会場表記を全件取り出した結果、
素朴な実装が壊れる形が揃っていた。

| 表記 | 何が問題か |
| --- | --- |
| `金沢・REDSUN` | **`・` の前は都道府県とは限らない。** 金沢は市名 |
| `韓国・SETi LIVE HALL` | **国内とも限らない** |
| `千葉・草ぶえの丘(千葉 佐倉) / Orange Shelter` | 単一会場だが `/` と括弧を含む |
| `愛知・大須RADHALL` / `愛知・大須RAD HALL` | **同じ会場が別表記で現れる** |
| （NULL） | 複数会場の告知は空欄で登録する（[ADR-0021](0021-register-appearances-without-timetable.md)） |

**表記ゆれと判定失敗は避けられない。** 自動判定だけに頼る設計にはできず、
**人が 1 か所直せば全体に効く**構造が要る。

## 決定

### 1. `venue` テーブルを足して会場を正規化する

正規化したキーで会場を 1 行にまとめ、そこに地域と `place_id` を持たせる。
`appearance` からは `venue_id` で参照する。

**`appearance.venue_name` は残す。** 原文の表記は出典に紐づく事実であり、
`venue` が持つのは代表表記である。`大須RADHALL` と `大須RAD HALL` は
同じ会場を指すが、**どちらの投稿がどう書いたかは変えてはいけない**。

キーの作り方は既存の `event_key`（[data-model.md](../data-model.md)「正規化ルール」）に倣う。
同じ流儀を 2 つ持つと片方だけ直す事故が起きるため、規則を揃える。

### 2. 地域は 8 地方 + 海外 + 不明の 10 区分にし、バックエンドが判定する

```
HOKKAIDO / TOHOKU / KANTO / CHUBU / KINKI / CHUGOKU / SHIKOKU / KYUSHU
OVERSEAS   海外
UNKNOWN    判定できない・会場が空欄
```

**判定は表示ではなくデータの分類である。** 47 都道府県の対応表と主要都市の別名
（金沢 → 石川 → 中部）を持つ知識であり、**将来のモバイル（NFR-07）でもう一度書きたくない**。
公開 API が `region` を返す形にする。

**色の割り当てはクライアントに置く。** どの地方を何色にするかは見た目の決定で、
バックエンドが知る必要が無い。

### 3. `place_id` を保存し、地図リンクは Maps URL で作る

```
https://www.google.com/maps/search/?api=1&query={会場名}&query_place_id={place_id}
```

Google 自身がこの組み合わせを推奨している——
「**Place ID をできる限り使い、宛先を確実に指定する**」。
名前だけの検索は同名の別施設に当たりうる。

`place_id` の解決には **Places API の Text Search (IDs Only)** を使う。
Google が「**Place ID を得るためのゼロコストな方法**」と明記しており、
月次の無料枠すら消費しない。

**呼び出しは会場ごとに 1 回だけ。** 閲覧のたびでも、取り込みのたびでもない。
実サンプルに出る会場は 15 種類で、生涯でも 100 種類に届かない見込み。

**`place_id` は無期限に保存してよい。** Google のポリシーが
キャッシュ制限の**例外**として明記している（他のフィールドは 30 日制限、
名前・評価・写真は保存不可）。

### 4. Places のデータは `place_id` 以外持たない

名前・住所・評価・写真を取得しない。会場名は**X の投稿から得た我々のデータ**を使う。

これにより**帰属表示（"Powered by Google"）が不要**になる。
帰属が要るのは Places のコンテンツを表示する場合であり、
`place_id` を保存して Google マップへ送るだけなら該当しない。

### 5. 解決は取り込みジョブから切り離す

**取り込みのトランザクションから Places API を呼ばない。**
X API の取り込みが Google 側の障害で失敗するのは筋が悪く、
`consecutive_failure_count` を無関係な理由で進めてしまう
（[x-integration.md](../x-integration.md)「エラーハンドリング」/ FR-43）。

取り込みがするのは**会場行を作ること**まで（地域はその場で判定、`place_id` は未解決）。
解決は管理画面からの操作、または独立した定期実行で行う。

### 6. 管理者が地域と place_id を上書きできる

**自動判定は必ず外れる。** 金沢のような市名、韓国のような国名、
未知の会場名がそれに当たる。**誤った地図リンクは、リンクが無いより悪い**——
ファンが違う場所へ向かう。

`venue` は 1 会場 1 行なので、**1 行直せば過去の全出演に効く**。
管理画面に会場の一覧と編集を置く。

## 選ばなかった案

**検索 URL だけを組み立てる（`place_id` を持たない）。**
DB もキーも要らず最も簡単だが、`大須RAD HALL` のような表記ゆれや
`千葉・草ぶえの丘(千葉 佐倉) / Orange Shelter` のような複合表記で外す。
**費用が同じ（どちらも $0）である以上、精度を捨てる理由が無い。**
ただし `place_id` が未解決の間はこの形にフォールバックする。

**`appearance` に `venue_region` と `venue_place_id` の列を足す。**
テーブルを増やさずに済むが、**同じ会場が現れるたびに同じ値が複製される**。
表記ゆれの補正も、`place_id` の修正も、行数ぶん繰り返すことになる。
「1 か所直せば全体に効く」という要件を満たせない。

**Places API を使わず、管理者が地図 URL を手で貼る。**
精度は最も高いが、**会場が出るたびに手作業が要る**。
IDs Only が無料である以上、まず自動で埋めて例外だけ直すほうが手数が少ない。

**判定をフロントエンドに置く。**
バックエンドのデプロイが要らなくなるが、47 都道府県の対応表と別名の知識を
**モバイル追加時にもう一度書く**ことになる。地域の分類は表示ではなくデータである。

## 影響

- **新しいシークレットが 1 つ増える**（Google Maps API キー）。[security.md](../security.md) T-08
- **外部依存が 2 つ目になる。** Places が落ちても、既に解決済みの `place_id` で
  地図リンクは出続ける。未解決の会場は検索 URL に落ちる
- **チップの色が意味を持つようになる。** いままで `chip-color.ts` は
  「意味は持たない（NFR-08）」と明記していた。この前提が変わる（次節）
- 色の区分が 6 から 10 に増える。**配色とコントラストの再検証が要る**

## 未決定: 色以外の手がかりをどう出すか

**色だけで地方を伝えることはできない。** WCAG 2.2 の達成基準 1.4.1「色の使用」
（レベル A）が「色を、情報を伝える唯一の視覚的手段にしない」と定めており、
NFR-08 はこれをそのまま書いたものである。

**凡例だけでは足りない。** WCAG の例示は、各要素が色**と数字の両方**を持ち、
凡例がその対応を示す形になっている。凡例は符号の読み方を教えるだけで、
**隣り合う 2 つのチップを見分ける役には立たない**。
`aria-label` も同様で、読み上げ利用者は救えるが、
色を区別しにくい「見えている」利用者は救えない。

チップは幅 360px のとき約 43.4px しかなく（[requirements.md](../requirements.md) NFR-06）、
出せる文字数が限られる。**時刻の前に都道府県 1 文字を置く案（`愛19:50`）は
見た目の理由で見送った。**

**候補は次のとおり。実装時に実物を見て決める。**

| 案 | 内容 | 懸念 |
| --- | --- | --- |
| A | チップに地方の記号（形）を添える | 10 区分を形で描き分けるのは 9px では厳しい |
| B | 遠征の日だけ日付の横に印を出す | 伝わるのは「地元か否か」の 2 値に縮む |
| C | チップの明度差を大きく取り、色以外でも並びが分かるようにする | WCAG は 3:1 の差を非色の手がかりとして認めるが、10 区分では設計が難しい |
| D | 出演一覧（カレンダー下）に地方のラベルを出す | カレンダーだけを見ている間は分からない |

**「色のみ」で確定する場合は、レベル A の不適合を承知のうえでの決定**として、
このファイルに追記すること。黙って落とさない。
