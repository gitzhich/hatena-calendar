# ADR-0021: タイムテーブル未確定の告知を、出演時刻なしで登録する

- status: 承認済み
- 日付: 2026-09-05

## 背景

公式は 1 つの公演を 2 回に分けて告知する。

```
① 公演情報解禁 / 出演日程解禁   日付・会場・イベント名・チケット
② タイムテーブル解禁            ①に加えて XINXIN の出演時刻・物販時刻
```

抽出仕様（[x-integration.md](../x-integration.md) 第 5.2 節）は
`XINXIN` を含む `🎤` 行があることを必須にしていたため、**①は全件 `UNPARSED`** に落ちていた。
本番のスモークテストでは未処理 4 件のうち 3 件がこの型で
（[runbook-x-api-setup.md](../runbook-x-api-setup.md) 付録）、頻度は低くない。

**①だけでも日付・会場・イベント名は確定している。** 登録できれば
タイムテーブルが出るまでの間もカレンダーに載り、ファンは「その日に予定がある」ことを
先に知れる（FR-01 / FR-03）。空欄補完（[data-model.md](../data-model.md) 第 7.1 節）が
②の時刻を同じ行へ入れる経路は既に動いていた。

対応を見送っていた理由は 1 つだけで、**判定条件**だった。
`🎤` 行は出演時刻の出どころであると同時に「これは公演告知だ」という証拠でもある。
外すだけでは、次回予告つきのお礼投稿（実サンプル 7.txt）を弾く根拠が無くなる。

## 決定

`XINXIN` を含む `🎤` 行が無い投稿を**経路 B** として扱い、
出演時刻を持たない出演情報を 1 件だけ作る。共通条件（日付候補・`📍`・イベント名）に
加えて、次の 3 つを**すべて**満たすことを要求する。

| # | 条件 |
| --- | --- |
| B-1 | `📍` の行から公演日がちょうど 1 つ取れる |
| B-2 | イベント名が**括弧付き**で取れる |
| B-3 | チケット URL（`🔗`）がある |

あわせて次を定める。

- **会場に `/` または `&` を含むなら、会場を空欄で登録する**
- **`🎤` 行があるのに `XINXIN` が入っていない投稿は経路 B に入れない**
- **時刻なしの登録で、同じ日・同じイベントの行が既にあるなら何もしない**

## 理由

### B-3（チケット URL）を軸にする

「これから行われる公演の告知にはチケット情報が付き、過ぎた公演のお礼投稿には付かない」
という**意味の違い**を条件にできる。実測でも分かれている。

| 集合 | `🔗` から URL を取れるか |
| --- | --- |
| 抽出している 16 件 | **16 / 16** |
| 対象外の 7 / 8 / 9 / 10 / 11.txt | **0 / 5**（`🔗` が 1 行も無い） |

利用者が本番の未処理投稿を 10 件以上確認し、`🔗` の無い情報解禁は 1 件も無かった。

要求するのは**マーカーの存在ではなく、スキーム付きの URL が取れること**。
実 API の本文はリンクを `https://t.co/…` に短縮して返すためスキームは必ず付く。

`🔗` は `ticket_url` として**保持する項目**である点も効いている。開演時刻（`⏰`）のような
保持しない項目を判定に使うと、**捨てる値の書き方が抽出の成否を決める**——
実サンプル 19.txt で実際に踏んだ失敗であり（第 5.3 節）、同じ形を繰り返さない。

### B-2（括弧付き）を足す

経路 B は `▪️` も `🎤` も無いため探索範囲が本文の末尾まで広がり、
**イベント名の連結を止めるのが空行だけ**になる。括弧も空行も無い投稿では
本文の後半をまるごと名前にしてしまう。

見た目が汚れるだけでは済まない。その名前から作られる `event_key` は
後続のタイムテーブル解禁のものと一致しないため、空欄補完が働かず、
**カレンダーに消えない重複行が残る**。

代償は、括弧の無いイベント名（20.txt 型）の情報解禁を取りこぼすこと。
実サンプル 23 件のイベント名 19 個のうち括弧が無いのは 1 個だけで、
落ちた投稿は未処理一覧から手で登録できる。
**取りこぼしは救えるが、公開された誤りは管理者が気づくまで残る**——
承認フローを持たない（[ADR-0003](0003-no-approval-flow.md)）以上、
判定条件が唯一の防壁になる。

### B-1（`📍` の行の日付）を足す

第 5.3 節は「`📍` の行に日付が無ければ探索範囲の全日付を候補にする」という
フォールバックを持つ。経路 A では `▪️` / `🎤` が探索範囲を切るので安全だが、
**経路 B では本文全体が候補になる**。

実サンプル 23.txt をフォールバックで処理すると候補が 8 個出る。
うち販売開始日の `8/9(日)` は 2026 年に実際に日曜であり、
**曜日検証を素通りする**。`📍` の行に限れば、第 5.1 節の基本形
`{M}/{D}({曜日})📍{都道府県}・{会場}` そのものが条件になる。

### 会場の羅列を入れない

この経路には枠ごとの `📍` が無く、羅列から出演会場を絞り込めない。
**羅列を入れると後から直らない**——空欄補完は値のある列を上書きしないため
（[ADR-0004](0004-fill-blanks-only.md)）、タイムテーブルが出た後も残り続ける。

```
1.txt  東京・渋谷音楽堂/Shibuya Milkyway/SHIBUYA THE GAME/Star Lounge/…（7 会場）
22.txt 愛知・NAGOYA ReNY limited & 栄Zephyr Hall（2 会場）
21.txt 東京・品川インターシティホール（単一。そのまま入れる）
```

区切りは `/` と `&` の 2 種類。実データはどちらも使う。
単一会場をわざわざ空欄にはしない——正しい値であり、早く出る価値が高い。

### `🎤` 行はあるが `XINXIN` が無い場合

タイムテーブルは**公開済みで、そこに XINXIN が載っていない**ということであり、
「まだ出ていない」とは別の状態である。時刻なしで登録すると誤情報になる。
この区別は既存の境界テストが捕まえた。

### 重複行のガード

一意キーは `(日付, event_key, 開始時刻)` である（[ADR-0012](0012-multi-slot-uniqueness.md)）。
`NULLS NOT DISTINCT` が保証するのは「時刻なしの行が 1 日 1 イベントにつき 1 行」までで、
`(d, k, NULL)` と `(d, k, 16:45)` は別の行として通る。

これまで時刻なしの行は管理者の手動登録からしか生まれず、
自動取り込みが後から時刻なしを作る経路が無かった。経路 B がその経路を開くため、
アプリ側で止める。通常は「情報解禁 → タイムテーブル解禁」の順に届いて
時刻なしの行が先にでき、②が空欄補完で埋める。逆順は
初回バックフィルの範囲に①が入らなかった場合などに起きる。

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| `🔗` だけを要求する（括弧を求めない） | 20.txt 型を拾えるが、括弧も空行も無い投稿で本文後半をイベント名にする。`event_key` が一致せず消えない重複行になる。**取りこぼしは手で救えるが、公開された誤りは救いにくい** |
| 括弧だけを要求する（`🔗` を求めない） | チケット情報がまだ無い告知も拾えるが、お礼投稿を弾く根拠がイベント名だけになる。7.txt は「会場行の次が空行」という書式の偶然で落ちているにすぎない |
| 告知の種別行（`🔸…解禁🔸`）を条件にする | 実データでマーカーが揺れる（17.txt は `🔶`、18.txt は `✈️`）。保持しない項目の書き方が抽出の成否を決める形になり、第 5.3 節で否定した設計に戻る |
| 出演者一覧（`【出演者(敬称略)】`）に XINXIN があることを条件にする | 保持しない項目であり、同じ問題を抱える。2.txt のように出演者一覧の無い告知もある |
| 会場を常に空欄にする | 規則は単純だが、21.txt のような単一会場（正しい値）まで見えなくなる |
| 会場の羅列をそのまま入れる | 告知の原文どおりではあるが、タイムテーブル後も 7 会場が残り、閲覧者はどこへ行くか分からない |
| 引き続き対象外にし、管理者が手で登録する | 今までの運用。頻度が低くなく（スモークテストで 4 件中 3 件）、速報性も落ちる |

## 結果

- 実サンプルは **23 件**（抽出する 16 件 / 抽出しない 7 件）になった
- [requirements.md](../requirements.md) の非スコープから
  「出演時刻が未確定の告知の自動登録」を外した
- [x-integration.md](../x-integration.md) 第 11.1 節（将来対応）を削除し、
  第 5.2 節に経路 B として本文化した
- 23.txt（複数日開催の出演日程解禁）は引き続き `UNPARSED`。
  「8/25 と 8/26 のどちらに出るか」はこの投稿からは決まらない
- **本番に溜まっている未処理投稿は救われない。** 投稿本文を保持していないため
  （LR-02）、再パースには X API の再取得が要る。効くのは今後の投稿だけで、
  既存分は手動登録のまま
- 9 つの変異（各条件を外す / 会場の空欄化を外す / 並び順を反転する / ガードを外す）が
  すべてテストに検出されることを確認した
