# ADR-0018: Neon を Singapore に置き、Fly.io を同居させる

- status: 承認済み
- 日付: 2026-09-03

## 背景

[architecture.md](../architecture.md) と
[runbook-deploy.md](../runbook-deploy.md) は当初、
**Fly.io も Neon も東京に置く**前提で書かれていた。日本のファンが見るサイトであり、
同一リージョンに揃えるのが自然だったため。

初回デプロイの作業中に、**Neon に東京（日本）リージョンが存在しない**ことが分かった。
選べるのは AWS の 8 か所で、アジア太平洋は **Singapore と Sydney のみ**。
Azure リージョンは新規プロジェクトを受け付けなくなっている。

**リージョンはプロジェクト作成後に変更できない。** 変えるには別プロジェクトを作って
データを移行する必要がある。実質的に不可逆な決定である。

## 決定

| 層 | リージョン | 変更可否 |
| --- | --- | --- |
| Neon | **Singapore**（`aws-ap-southeast-1`） | **不可逆**。作成後に変更できない |
| Fly.io | **Singapore**（`sin`） | 可能（`fly.toml` を変えて再デプロイ） |
| Vercel Functions | **Tokyo**（`hnd1`） | 可能（`frontend/vercel.json` の 1 行） |

**Vercel のリージョンは `frontend/vercel.json` に置く。** コンソールの設定にすると、
既定の `iad1`（ワシントン DC）のまま気づかない事故が起きる。

## 理由

### どこかで太平洋を跨ぐことは避けられない

Neon が Singapore に固定される以上、日本とシンガポールの往復はどこかで必ず入る。
決めるべきは**どこで跨ぐか**であって、跨がないようにはできない。

### バックエンドと DB を同居させる

構成は `ブラウザ → Vercel（ISR キャッシュ） → Fly.io → Neon`。
**閲覧者の大半はキャッシュで返り、バックエンドまで届かない。**
届くのは ISR の再検証・管理画面・取り込みジョブで、
**このうち管理画面と取り込みは 1 リクエストで複数回クエリを打つ。**

| 構成 | 公開ページ（クエリ 1 回） | 管理画面（クエリ 2 回） | 取り込み（クエリ数十回） |
| --- | --- | --- | --- |
| Fly `nrt` + Neon `sin` | 約 170ms | 約 310ms | **1 クエリごとに +70ms** |
| **Fly `sin` + Neon `sin`** | 約 165ms | **約 170ms** | **ほぼゼロ** |

同居させると、跨ぐのが「クエリごと」から「リクエストごと 1 回」に減る。
公開ページは互角だが、複数クエリを打つ経路で差がはっきり出る。

### Vercel だけ東京に残す

**ユーザーに近い側はユーザーの近くに置く。** Vercel の関数が行う仕事のうち、
バックエンドを呼ばないもの（停止ページ、ログイン画面の描画、404、
セッション Cookie の復号）は東京のほうが速い。

バックエンドを呼ぶ経路では `sin1` のほうがわずかに速いが（管理画面で約 9ms）、
差は誤差の範囲にある。一方で**バックエンドを呼ばない仕事は 60ms 以上変わる**。

**この選択は可逆である。** `vercel.json` の 1 行で変えられるため、
NFR-01 の実測が想定と違えば入れ替えればよい。
**不可逆な決定（Neon）を慎重に行い、可逆な決定は測ってから調整する。**

将来 Neon が東京リージョンを持てば、Fly.io を `nrt` に戻すだけで最適になる。
Vercel 側は変えなくてよい。

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| Neon を Sydney に置く | 東京からの距離が Singapore より遠い。選ぶ理由がない |
| Neon の Azure リージョンを使う | **新規プロジェクトを受け付けていない** |
| Fly.io を `nrt` のままにする | 1 クエリごとに往復が乗る。取り込みジョブは 1 回の実行で数十回クエリを打つため、実行時間がそのぶん伸びる。管理画面も体感で遅くなる |
| Vercel を `sin1` にして全部同居 | バックエンドを呼ぶ経路はわずかに速いが、**呼ばない仕事が 60ms 以上遅くなる**。Neon が東京を持ったときに 2 か所を直すことになる |
| Vercel を既定（`iad1`）のままにする | 日本の閲覧者のリクエストが毎回アメリカ経由になる。**新規プロジェクトの既定値なので、明示しないとこうなる** |
| 別の DB サービスに変える | [ADR-0009](0009-hosting.md) の選定をやり直すことになる。無料枠・PostgreSQL 互換・運用の手間で Neon を選んでおり、リージョンだけで覆すほどの差ではない |

## 結果

- `backend/fly.toml` の `primary_region` が `sin`
- `frontend/vercel.json` が `regions: ["hnd1"]` を持つ（**新規ファイル**）
- [runbook-deploy.md](../runbook-deploy.md) の第 2.1 節・第 3 章・第 5 章を更新した。
  **Vercel の関数リージョンは元の手順書に記載が無く、既定の `iad1` のまま
  デプロイされるところだった**
- [architecture.md](../architecture.md) 第 8 章にリージョンの表を足した
- **NFR-01 の実測時にこの構成を評価する。** 想定と違えば Vercel 側から調整する
