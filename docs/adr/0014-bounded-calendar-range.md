# ADR-0014: 公開カレンダーが受け付ける年月の範囲を有限にする

- status: 承認済み
- 日付: 2026-09-01

## 背景

[security.md](../security.md) T-04 は「攻撃者が公開ページを連打して
Neon の無料枠を枯渇させ、課金を発生させずにサイトを停止させられる」脅威を挙げ、
主な対策を **ISR キャッシュ**としていた。

しかしこの対策には穴があった。公開カレンダーのルートは `[year]/[month]` であり、
**年月ごとに別のキャッシュエントリになる**。当初の FR-05 は
「未来方向の移動に上限を設けない」と定めていて、年月の妥当性検証もなかった。

```
/9999/12  /9998/12  /9997/12 ...
    → すべて別のキャッシュキー
    → すべてキャッシュミス
    → すべて Server Component → Spring Boot → Neon に到達する
```

ISR が効くのは**同じ URL が繰り返し要求される場合**だけで、
年月を変え続けられると防御にならない。
[api.md](../api.md)「期間内の出演情報一覧」の「期間の上限 62 日」は 1 リクエストの幅を縛るだけで、
リクエストできる月の**種類数**を縛らない。

## 決定

**表示できる年月を「サービス開始月 〜 現在 +24 か月」に限定し、
範囲外は `404` を返す。**

検証は **Server Component がデータを取得する前**に行い、範囲外は `notFound()` にする。
キャッシュエントリはできても **DB クエリは発生しない**。

公開 API 側でも `from` / `to` が同じ範囲を外れたら `400` を返す（多層防御）。

## 理由

- **キャッシュキーの集合が有限になる。** 埋め尽くされても DB への到達は
  有限回で止まり、無料枠の枯渇に到達しない
- **FR-05 の意図を損なわない。** 「上限を設けない」の狙いは
  「データがない月も空のカレンダーとして見に行ける」ことであり、
  +24 か月あれば実用上は無制限と変わらない。告知は数か月先までしか出ない
- **取得の前に弾くことが本質。** キャッシュエントリが増えること自体は
  Vercel 側の問題で、こちらの無料枠を削るのは DB クエリのほう

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| 範囲外を最も近い端の月へリダイレクトする | DB 到達は同じく有限になるが、共有された URL と実際の表示が食い違う。FR-05 の「共有とリロードで同じ画面になる」と噛み合わない |
| FR-05 を変えず、レート制限だけで守る | 単一 IP の連打は止まるが、複数 IP から年月を変えて回されるとキャッシュミスが累積して DB に届き続ける |
| `generateStaticParams` で全月を事前生成し `dynamicParams: false` にする | 範囲外が自動的に `404` になる点は良いが、**全月ぶんのレンダリングがビルド時に走り、Vercel のビルドがバックエンドの生死に依存する**。バックエンドが落ちている間デプロイできなくなる |

## 結果

- FR-05 の受入基準が変わった。「未来方向の移動に上限を設けない」を
  範囲の明示と `404` の要件に差し替えた
- レート制限の置き場所も見直した。Spring Boot から見た送信元は
  Vercel の egress IP なので、そこで IP 単位に絞ると全閲覧者が巻き添えになる。
  **実クライアント IP が見える Next.js の middleware に置く**
  （[architecture.md](../architecture.md)「公開ページのレート制限」）
- T-04 の対策表を書き直した。ISR を筆頭対策として挙げるのをやめ、
  範囲の限定と組み合わせて初めて防御になることを明記した
- サービス開始月は固定値として持つ。過去の出演情報は削除せず保持するため
  （[requirements.md](../requirements.md)「保持期間」）、下限は動かさない

## 更新履歴

- 2026-09-01: 実装して分かった点を追記（決定内容の変更なし）。
  **`generateStaticParams` を空配列で置く必要がある。** これが無いと
  Next.js は `[year]/[month]` を純粋な動的レンダリングとして扱い、
  応答が `no-store` になって ISR が効かない。実測で
  `Cache-Control: private, no-cache, no-store` を確認した。
  その状態では毎リクエストが DB へ到達し、**本 ADR が防ごうとしている
  T-04 の経路が、範囲内の年月に対して開いたままになる**。
  空配列を返せば「ビルド時は作らないが、初回アクセス時に生成して ISR で持つ」
  になり、却下案（全月を事前生成）のビルド依存も避けられる。
  追加後は `x-nextjs-cache: MISS → HIT` と
  `s-maxage=300, stale-while-revalidate` を確認済み

- 2026-09-03: **サービス開始月の値を文書に置いた**（決定内容の変更なし）。
  本 ADR は「固定値として持つ」としか書いておらず、実際の値
  （`2026-01`）は実装だけが持っていた。[security.md](../security.md)「レート制限の構成と値」が
  この値から「表示できる月数」を導いてレート制限の根拠にしているため、
  値が無いと検算できない。**正本は [requirements.md](../requirements.md) FR-05 の
  受入基準**とし、`CalendarRange` と `frontend/lib/calendar-range.ts` が
  それに従う関係にした。あわせて「サービス開始月 +24 か月」とも読めた
  FR-05 の記述を「**現在（JST）の月 +24 か月**」に書き切った（本 ADR と実装が
  元からそうだった）
