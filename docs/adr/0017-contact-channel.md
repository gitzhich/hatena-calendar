# ADR-0017: 削除要請の窓口をサイト専用のメールアドレスにする

- status: 承認済み
- 日付: 2026-09-03

## 背景

[requirements.md](../requirements.md) LR-05 は「サイト上に問い合わせ・削除要請のための
連絡手段が記載されている」ことを求めているが、**手段そのものが決まっていなかった**
（同 第 12 章 未決定事項の**「削除要請の連絡手段」**）。
デプロイ前に決着させる必要がある。

前提が 2 つある。

- 運用者は**個人であり、既存の個人用メールアドレスを公開したくない**
- 要請を出してくる相手として想定されるのは XINXIN の運営・事務所であり、
  **摩擦が少なく、双方に記録が残る手段**であることが望ましい

## 決定

**サイト専用のメールアドレスを 1 つ用意し、それを窓口として掲載する。
受信は運用者の個人受信箱へ自動転送する。**

掲載箇所は 2 つ。

| 掲載先 | 理由 |
| --- | --- |
| 全ページのフッタ（`Disclaimer`） | LR-01 と同じ場所。要請者が探さずに見つけられる |
| 停止ページ（`/unavailable`） | 停止中こそ要請の最中である（[ADR-0013](0013-site-kill-switch.md)） |

**アドレスは `frontend/lib/contact.ts` の定数 1 か所に置く。** 掲載箇所が増えても
食い違わせないため、および将来アドレスを変えるときに 1 行で済ませるため
（[coding-guidelines.md](../coding-guidelines.md) 第 11 章）。

**難読化（画像化・JavaScript による組み立て）はしない。** アクセシビリティを落とすうえ、
効果が限定的である。専用アドレスなので、スパムが来ても個人の受信箱は汚れない。
Gmail はスパム判定したメールを転送しないため、転送先にも届かない。

## 理由

### 停止中に動かない窓口は意味がない

`frontend/proxy.ts` は `SITE_DISABLED=true` のとき、`/admin` と `/unavailable` を除く
**全パスを停止ページへ書き換える**（[ADR-0013](0013-site-kill-switch.md)）。
つまり**サイト内に問い合わせフォームを作ると、削除要請でサイトを止めた瞬間に
窓口ごと消える**。最も必要な場面で使えない。

連絡手段は**サイトの外で完結するもの**でなければならない。この制約だけで、
自前のフォームは選択肢から外れる。

### 転送しないと見落とす

**誰も見ない窓口は無いのと同じ**で、削除要請を見落とすのが最悪の失敗である。
専用アカウントを作るだけでなく、**個人の受信箱へ転送する**ところまでを決定に含める。

### メールなら要件が増えない

フォームでメールアドレスを取得すると、個人情報保護法上、利用目的の明示が必要になり、
実務上はプライバシーポリシーの掲示に行き着く。これは
[requirements.md](../requirements.md) 第 12 章の「アクセス解析の導入有無」と同じ構図で、
**MVP の要件が 1 つ増える**。メールで受け取るだけならその画面を作らずに済む。

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| サイト内に問い合わせフォームを実装 | **停止中に到達できない**（上記）。加えて送信基盤（Resend 等）の依存が増え、プライバシーポリシーの掲示も要る |
| 外部フォーム（Google フォーム等） | 停止中も動くが、利用目的の明示が要る点は同じ。返信は結局メールになるため、メール窓口を別に持つことになる。**補助手段としてなら後から足せる** |
| 独自ドメイン + Cloudflare Email Routing | `contact@<domain>` が使え信頼性は最も高い。ただし **Email Routing は受信専用**で、返信するには別途 SMTP が要る。Gmail の "Send mail as" で代用すると**返信ヘッダから個人のアドレスが見える経路が残り**、前提に反する。ドメイン取得の判断も別途必要になる |
| マスク / エイリアス（iCloud Hide My Email、Firefox Relay 等） | **サービス登録用の使い捨てアドレス**であり、公開窓口の用途ではない。ランダム文字列で信頼性が低く、無料枠には帯域や返信の制限がある |
| X の DM | 情報源が X なので相手も X にいるが、DM は開放設定が要り、通知に埋もれやすく記録も弱い。**補助として併記するのは妨げない** |
| 個人の既存アドレスを掲載 | 前提により却下 |

## 結果

- `frontend/lib/contact.ts` が窓口アドレスを持つ。**掲載箇所はここだけを参照する**
- `Disclaimer` を `app/layout.tsx` へ移した。従来は `CalendarPage` の中にあり、
  **`/unavailable` など通らないページには出ていなかった**。LR-01 の
  「全ページ」を満たしていなかったのを、この作業で併せて直している
- 要請時に記載してほしい項目（対象の出演情報 / 該当ページの URL / 要請の理由）を
  画面に明示する。往復を減らすため
- [requirements.md](../requirements.md) 第 12 章 未決定事項の
  **「削除要請の連絡手段」**が決着した（項目は削除済み）

### 将来の変更

サイト用に独自ドメインを取る判断をしたら、`frontend/lib/contact.ts` の 1 行を
差し替えるだけで `contact@<domain>` へ移せる。そのときは送信経路
（返信元に個人のアドレスが出ないこと）を確かめること。
