# ADR-0011: 深夜公演を時刻が実際に属する暦日に配置する

- status: 承認済み
- 日付: 2026-08-29

## 背景

ライブハウスの告知では「26:00」のように 24 時を超える時刻表記が使われる。
これは告知上「9/16 の深夜」を意味するが、実際の時刻は 9/17 の 02:00 である。
どちらの暦日に置くかでカレンダー上の表示位置が 1 日ずれるため、
`appearance_date` の決め方に直結する。

CLAUDE.md と [requirements.md](../requirements.md) では暫定的に
「実際に属する暦日」としつつ、告知どおりの日付で探すファンの直感とずれる点を
未決定事項として残していた。実装前に結論を出す必要があった。

## 決定

**時刻が実際に属する暦日に配置する。**

```
告知「9/16(火) ... 🎤26:00-26:30 XINXIN出演」
  → appearance_date        = 2026-09-17   ← 翌日
    performance_start_time = 02:00
    performance_end_time   = 02:30
```

出演枠そのものが日を跨ぐ表記（「23:50-24:30」）は自動登録せず、
投稿を `UNPARSED` として管理者に回す。

## 理由

- **24 時以上の時刻をそのまま保持できる型がない。** PostgreSQL の `TIME` は
  `24:00:00` までしか受け付けず、Java の `LocalTime` の上限は `23:59:59.999999999`。
  `26:00` を保持するには別列か文字列にするしかなく、
  ソート・範囲検索・表示のすべてで特別扱いが必要になる
- **「その日の出演」の判定（JST 00:00〜23:59、NFR-05）と一致する。**
  日付をずらさない案では、17 日 02:00 の公演が 16 日のセルに出る一方で
  判定ロジックは 17 日と答えるため、同じ値に 2 つの解釈が生まれる
- **時系列の順序が壊れない。** 16 日夜の公演と 16 日深夜（＝17 日未明）の公演が
  両方ある場合、日付をずらさずに持つと同じ暦日に `20:00` と `26:00` が並ぶ。
  `26:00` を `02:00` に落として同じ日に置けば、順序が逆転する
- 変換規則は機械的に決まる（24 を引いて 1 日進めるだけ）ので、
  自動取り込みで安全に処理できる

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| 告知どおりの日付に置く（26:00 を 9/16 に置く） | 26:00 を保持する型がない。文字列や分数で持つと全クエリで特別扱いが要る |
| 日跨ぎフラグ列を追加する | 列が増え、表示・ソート・月次クエリのすべてでフラグを考慮する必要がある。深夜公演の頻度に見合わない |
| 深夜公演を `UNPARSED` にして管理者に回す | 変換規則が機械的に決まるものを手作業に落とす理由がない。管理コストが増えるだけ |

## 結果

- 告知の日付で探すファンとは、カレンダー上の位置が 1 日ずれる。
  前日のセルにも併記するような表示上の補完は **MVP では行わない**
- 出演枠が日を跨ぐケースだけは自動登録の対象外になる。
  実サンプルの出演枠はいずれも 15〜30 分で、この形の告知は想定していない
- `appearance` の出演時刻の順序制約
  （`appearance_performance_time_order`: `performance_start_time <= performance_end_time`）は
  変更しない
- 日付の繰り上げで月・年をまたぐ（8/31 の 26:00 は 9/1 の 02:00）ため、
  日付加算はカレンダー演算で行う。境界のテストを必須とする
- CLAUDE.md と requirements.md の未決定事項から本項目を削除した
