## 1. 目的と背景

### 1.1 背景

XINXIN の出演情報は公式 X で告知されるが、タイムラインは時系列で流れていくため、
「今週末どこで見られるか」「来月の予定はどうなっているか」を知るには過去の投稿を
遡る必要がある。告知は日常的な投稿に埋もれ、日付・会場・出演時間が別々の投稿に
分かれることもあり、予定の全体像を掴みにくい。

### 1.2 目的

公式 X で告知された出演情報を日付単位で集約し、カレンダー上で一覧できるようにする。
ファンが「いつ・どこで見られるか」を数秒で把握できる状態を目指す。

### 1.3 位置づけ

本アプリは**ファンが個人で制作する非公式のツール**である。XINXIN および運営とは
関係がなく、公認も受けていない。正確かつ最新の情報の一次情報源は常に公式 X であり、
本アプリはその補助的な閲覧手段に過ぎない。この位置づけは FR-07 / LR-01 として
機能要件に落とし込む。

## 2. 用語定義

以降の設計文書とコードの命名は、この定義に揃える。

| 用語 | 英名 | 定義 |
| --- | --- | --- |
| 情報源アカウント | SourceAccount | 出演情報の取得元となる X アカウント。MVP では XINXIN 公式の 1 件のみ |
| 投稿 | Post | 情報源アカウントの X 上のポスト |
| 出演情報 | Appearance | 「いつ・どこで・何のイベントに出演するか」を表すデータ単位。**登録された時点で閲覧者に公開される** |
| 登録経路 | SourceType | その出演情報が自動取り込みで作られたか、管理者が手動で作ったかの区別 |
| 未処理投稿 | UnparsedPost | 取り込んだが出演情報を抽出できなかった投稿。管理者が手動で処理する |
| 管理者 | Admin | 本アプリの唯一の運用者。自動登録の点検・手動登録・修正・削除を行う |
| 閲覧者 | Visitor | 認証なしで出演情報を閲覧する利用者 |

## 3. 想定利用者とロール

システムに存在するロールは以下の 2 つのみ。**一般ユーザーのアカウント登録は存在しない。**

### 3.1 閲覧者（Visitor）

- 認証不要
- XINXIN のファン。**スマートフォンからの閲覧が主**と想定する
- 出演情報の閲覧のみが可能で、データを変更する手段を一切持たない

### 3.2 管理者（Admin）

- **単一アカウント**。運用者本人のみ。アカウントの新規登録機能は設けない
- 認証必須
- 自動登録された出演情報の点検と訂正、出演情報の手動登録・編集・削除を行う

## 4. スコープ

### 4.1 MVP スコープ

- 公開カレンダー（月表示）と出演詳細の閲覧（FR-01〜FR-08）
- 管理者による点検・手動登録・編集・削除（FR-20〜FR-25）
- X API からの差分取り込みと、抽出した出演情報の自動登録（FR-40〜FR-43）

### 4.2 非スコープ

「なぜ今やらないか」を残す。将来やる場合はこの表から要件へ昇格させる。

| 項目 | 見送る理由 |
| --- | --- |
| 一般ユーザーのアカウント登録・お気に入り・通知 | 閲覧だけなら認証は不要。認証を入れると個人情報保護の要件が一気に増える |
| 複数アイドル / 複数グループ対応 | 情報源が増えると重複排除とデータモデルが複雑化する。まず 1 グループで完成させる |
| 週表示 / 日表示 / リスト表示の切り替え | 月表示だけで「いつ見られるか」の目的は満たせる |
| 過去投稿の完全なバックフィル | X API の遡り上限（約 3,200 件）により完全性を保証できない。best-effort に留める |
| 出演情報の全文検索・会場別の絞り込み | データ量が少ないうちは月移動で足りる |
| 取り込み結果の承認フロー | 承認を挟むと管理者が作業するまで情報が公開されず、告知の速報性が失われる。単一管理者では承認作業がボトルネックになり、運用の手間も大きい。抽出精度を高めることで対応し、誤りは事後の修正で直す（FR-22, FR-41、`docs/adr/0003-no-approval-flow.md`） |
| スマホアプリ（Expo / EAS） | Web を完成させ、バックエンドが安定してから着手する。API 設計だけ先に配慮する（NFR-07） |
| **出演時間の訂正の自動反映** | 「本日の出演は 15:00-15:15 に変更」のような訂正告知。日付が「本日」としか書かれず、かつ確定済みの値の上書きになるため `docs/adr/0004-fill-blanks-only.md` と衝突する。管理者が手で直す（`docs/x-integration.md`「出演時間の訂正（実サンプル 8.txt / 11.txt）」） |

## 5. ユースケース

### UC-01 今週末どこで見られるか調べる

閲覧者がスマホでサイトを開き、当月カレンダーから出演がある日を見つけ、
その日の会場と時刻を確認する。→ FR-01, FR-02, FR-03, FR-04, FR-08

### UC-02 特定の日の出演詳細を確認しチケットを取る

閲覧者が日付を選び、イベント名・会場・出演時間を確認し、チケットリンクへ移動する。
情報が古い可能性を考え、出典の X 投稿で裏を取る。→ FR-03, FR-04, FR-06, FR-07

### UC-03 管理者が自動登録された情報の誤りを訂正する

管理者がログインし、直近に自動登録された出演情報を一覧で確認する。日付や会場に誤りが
あればその場で修正し、出演告知ではない投稿から誤って作られたものは削除する。
公式が日程変更を告知した場合も、該当する既存の出演情報を手で直す。
→ FR-20, FR-24, FR-22, FR-23

### UC-04 管理者がパース失敗分を手動登録する

自動抽出に失敗した投稿の一覧を開き、内容を読んで出演情報を手で登録する。
出演告知ではない投稿は対象外にする。→ FR-20, FR-25, FR-21

## 6. 機能要件

各要件は「要件文」と「受入基準」で構成する。受入基準は**テストコードに落とせる粒度**で書く。

### 6.1 閲覧者向け機能

#### FR-01 月表示カレンダーの表示

閲覧者は、指定した年月の出演予定をカレンダー（月グリッド）で閲覧できる。

**受入基準**

- 認証なしでトップページにアクセスすると、当月（JST 基準）のカレンダーが表示される
- カレンダーは 7 列のグリッドで、当月のすべての日付を含む
- グリッドを埋めるために表示される前月・翌月の日付は、当月の日付と視覚的に区別される
- 当日（JST 基準）が視覚的に強調される

#### FR-02 出演がある日のマーク

出演情報が存在する日は、カレンダー上でそれと分かる表示になる。

**受入基準**

- 出演情報が 1 件以上ある日にはマークが表示される
- 同じ日に複数件ある場合、複数あることが分かる（件数表示、またはマークの反復）
- マークは**色のみに依存しない**（形状または文字を伴う。NFR-08 と対応）

#### FR-03 日付選択によるその日の出演一覧

閲覧者は、カレンダー上の日付を選択して、その日の出演情報一覧を表示できる。

**受入基準**

- 出演がある日を選択すると、その日の出演情報が**出演開始時刻の昇順**で一覧表示される
- 出演開始時刻が未設定の出演情報は、時刻ありのものの後に表示される
- **同じイベントに複数回出演する場合**（1 つのフェスで 2 つの会場に出るなど）、
  それぞれを別の項目として表示し、会場と時刻で区別できる
- 出演がない日を選択した場合、「予定なし」と分かる表示になる（無反応にしない）
- 日付の選択はキーボード操作（Tab での移動、Enter での決定）で行える

#### FR-04 出演詳細の表示

出演情報の詳細として、日付・イベント名・会場・XINXIN の出演時刻・物販時刻・
チケットリンク・出典 URL を表示する。

**受入基準**

- 必須項目（日付、イベント名）は常に表示される
- **出演時刻が無い場合は「時刻未定」と表示する**（タイムテーブル未確定。カレンダーチップと同じ文言）
- 任意項目（会場、物販時刻、チケットリンク）は、値がない場合**その欄自体を表示しない**
  （空欄で埋めない。確定情報だと誤解させない）
- 出演時刻と物販時刻は別の項目として表示し、どちらの時間帯かが判別できる
- 会場・物販・チケットの不明な値を空文字やプレースホルダで埋めない
- 出典 URL は常に表示される（FR-06）
- 外部リンクには `rel="noopener noreferrer"` を付与する

#### FR-05 前月・翌月への移動

閲覧者は表示する月を切り替えられる。

**受入基準**

- 前月・翌月へ移動する操作があり、移動後の年月が URL に反映される
- 年月を含む URL を直接開くと、その月のカレンダーが表示される（共有とリロードで同じ画面になる）
- 表示できるのは **`2026-01`（サービス開始月）から、現在（JST）の月 + 24 か月まで**。
  この範囲内であれば、データがない月も空のカレンダーを表示する
- **上限の起点は「現在」であって「サービス開始月」ではない。**
  範囲は毎月 1 か月ずつ広がる。[security.md](security.md)「レート制限の構成と値」が
  この月数からレート制限の値を導いているため、起点を取り違えると検算が合わない
- **値の正本はこの受入基準。** 実装は `CalendarRange.SERVICE_START` /
  `CalendarRange.MAX_FUTURE_MONTHS`（バックエンド）と
  `frontend/lib/calendar-range.ts`（フロント）が同じ値を持つ。
  片方だけ変えると、フロントが通した年月をバックエンドが `400` で弾く
- **範囲外の年月を指す URL は `404` を返し、バックエンドへの問い合わせを発生させない**。
  年月ごとにキャッシュが分かれるため、範囲を絞らないとキャッシュキーを
  無制限に増やされ、そのすべてが DB に到達する
  （[ADR-0014](adr/0014-bounded-calendar-range.md)、`docs/security.md` T-04）

#### FR-06 出典 X 投稿へのリンク

すべての出演情報は根拠となった X 投稿の URL を持ち、詳細から辿れる。

**受入基準**

- 自動取り込み由来の出演情報は、出典 URL を必ず持つ
- 手動登録の出演情報も**出典 URL を必須入力**とする（根拠のないデータを公開しない）
- 出典は URL へのリンクとして表示し、投稿本文の転載を伴わない（LR-02）

#### FR-07 非公式である旨の免責表示

本アプリが非公式であること、最新情報は公式 X で確認すべきことを明示する。

**受入基準**

- すべてのページのフッタに、非公式であり運営とは無関係である旨の記載がある
- 「最新・正確な情報は公式 X をご確認ください」という趣旨の文言と、公式 X へのリンクがある
- カレンダー画面から、スクロールせずに免責表示へ到達できる導線がある（フッタへのリンク等）

**文面は `frontend/components/Disclaimer.tsx` が正本。** 2026-09-03 から本番で
稼働している文面をそのまま正式版とする。仮置きではない。

#### FR-08 データ最終更新日時の表示

閲覧者がデータの鮮度を判断できるようにする。

**受入基準**

- 最後に取り込みが成功した日時を JST で表示する
- 取り込みが 24 時間以上成功していない場合、情報が古い可能性がある旨を併記する
- **一度も取り込みが成功していない場合は最終更新日時を表示せず、警告も出さない。**
  併記する日時が無い場面で警告だけを出しても閲覧者は行動を決められず、
  手動登録だけで運用している間は警告が出続けて読み飛ばされる
  （判定は [api.md](api.md)「データの状態」）

### 6.2 管理者向け機能

#### FR-20 ログイン / ログアウト

管理者は認証を経て管理機能を利用できる。

**受入基準**

- `/admin` 配下は未認証でアクセスすると認証画面へ誘導される（デフォルト拒否。NFR-03）
- 認証は**環境変数で与えられた単一アカウント**で検証する。DB にユーザーテーブルを持たない
- パスワードはハッシュ（BCrypt 等）で保持し、平文を保存・ログ出力しない
- ログイン失敗時のメッセージから、ユーザー名の存否を判別できない
- 連続失敗に対してレート制限が働く（NFR-03）
- ログアウトによりセッション（またはトークン）が無効化される

#### FR-21 出演情報の手動登録

管理者は出演情報を直接登録できる。

**受入基準**

- 日付・イベント名・出典 URL を必須とし、欠けている場合は**サーバ側で**拒否する
- 日付・イベント名・出演開始時刻の組が既存の出演情報と一致する場合、
  **エラーを返して重複登録を防ぐ**（既存を上書きしない。修正は FR-22 で行う）。
  イベント名の一致は表記ゆれを正規化したうえで判定する
- 同じ日の同じイベントでも、**出演開始時刻が異なれば別の出演情報として登録できる**
  （1 つのイベントで複数回出演する告知があるため。[ADR-0012](adr/0012-multi-slot-uniqueness.md)）
- 出演開始時刻を指定しない出演情報は、同じ日の同じイベントにつき 1 件しか登録できない
- 登録した出演情報は即座に公開される
- すべての入力値がサーバ側で検証される（NFR-03）

#### FR-22 出演情報の編集

管理者は登録済みの出演情報を修正できる。**自動取り込みされた情報の誤りを訂正すること**が
主な用途となる。

**受入基準**

- 自動登録・手動登録のどちらの出演情報も編集できる
- 編集内容は保存後ただちに公開画面へ反映される
- 編集日時が記録される
- 自動取り込みは値の入っている列を上書きしないため（FR-41）、
  **手動で修正した内容が後続の取り込みで巻き戻ることがない**
- 公式が日程変更・出演中止を告知した場合は、管理者が該当する既存の出演情報を
  修正または削除して対応する（システムが自動で書き換えることはしない）

#### FR-23 出演情報の削除

管理者は誤って登録した出演情報を削除できる。

**受入基準**

- 削除した出演情報は公開画面から即座に見えなくなる
- 誤操作防止のため、削除前に確認操作を挟む
- 削除しても取り込み済み投稿の記録は残り、
  **同じ投稿から再び出演情報が作られない**（再処理時の冪等性）
- 出演告知ではない投稿から誤って作られた出演情報を削除できる
- 公式の変更告知により同一イベントが二重に登録された場合、古い方を削除できる

#### FR-24 自動登録された出演情報の確認

管理者は、自動取り込みで登録された出演情報を一覧し、誤りがないか点検できる。
公開の可否を決める承認手続きではなく、**公開後の事後点検**のための機能である。

**受入基準**

- 自動登録された出演情報を、登録日時の新しい順に一覧できる
- 各項目に抽出元の投稿 URL が表示され、原文と突き合わせて確認できる
- 一覧から編集（FR-22）と削除（FR-23）へ移動できる
- この一覧は管理者専用であり、閲覧者はアクセスできない

#### FR-25 未処理投稿の一覧と手動登録

抽出に失敗した投稿を取りこぼさない。

**受入基準**

- 出演情報を抽出できなかった投稿を一覧できる
- 一覧から手動で出演情報を作成でき、その際**投稿 URL が出典として引き継がれる**
- 出演情報を作成した投稿は**処理済みとして扱われ、以降この一覧に現れない**
- 出演告知ではない投稿を「対象外」に分類でき、以降一覧に現れない

### 6.3 システム / バッチ機能

#### FR-40 X API からの差分取り込み

情報源アカウントの新規投稿のみを定期的に取得する。
情報源は **`@xinxin_official`（XINXIN 公式）1 件**に確定している。
解決済みのユーザー ID は
[docs/runbook-x-api-setup.md](runbook-x-api-setup.md) 付録 C.3 にある。

**受入基準**

- 取得済みの**最大 tweet_id を永続化し、次回リクエストの `since_id` に必ず渡す**
- `since_id` を渡さずに取得する経路（全件取り直し）が実装に存在しない
- リクエストに `exclude=replies,retweets` を指定する
- 新規投稿がない場合、取得リソース数 0 で正常終了する
- `note_tweet` を持つ投稿では、`text` ではなく `note_tweet` の本文を処理対象とする
- 情報源アカウントのユーザー ID は初回に一度だけ解決して永続化し、
  以降 username からの解決 API を呼ばない
- 取り込みが行うのは**新規追加と、既存の出演情報の空欄補完のみ**。
  値が入っている列を上書きしない（FR-41）

#### FR-41 投稿からの出演情報の抽出と登録

取得した投稿から出演情報を抽出し、**承認を挟まずに登録して公開する**。
抽出は失敗する前提で設計する。

**受入基準**

- 抽出に成功した投稿は出演情報として登録され、ただちに閲覧者へ公開される
- 登録された出演情報は登録経路が「自動」として記録され、FR-24 の点検対象になる
- 自動登録の対象は**出演時刻まで確定した公演告知に限る**。
  出演時刻が読み取れない告知は登録せず、未処理投稿として残す
  （対象とする投稿型は `docs/x-integration.md`「抽出対象の判定」）
- 抽出に失敗した投稿は**破棄されず**、未処理投稿として残る（FR-25）
- 同一投稿から重複した出演情報を作らない（再処理時も同じ）
- すべての自動登録に、抽出元の投稿 URL が紐づく
- 告知に年が書かれていない場合（「9/16(水)」のみ）、投稿日時から年を補い、
  **併記された曜日と一致するか検証する**
- 抽出結果が既存の出演情報と**同じ公演を指す**場合は新しい行を作らず、
  **値が未設定の項目だけを埋める**。公式が「公演情報解禁」と「タイムテーブル解禁」を
  分けて告知するため（`docs/x-post-sample/` の実サンプル参照）。
  照合の規則は `docs/data-model.md`「追加告知による空欄補完」
- 1 つの告知に**複数の出演枠**が含まれる場合、枠ごとに別の出演情報を作る
  （同じ日・同じイベントでも出演開始時刻で区別する。[ADR-0012](adr/0012-multi-slot-uniqueness.md)）
- 画面に表示するイベント名は**告知の原文**であり、照合用の正規化値を表示に使わない
- 補完の際、既に値が入っている項目は上書きしない
- 補完が起きたとき、出典 URL はその告知のものへ更新する
- `docs/x-post-sample/` の実サンプルに対する抽出テストが存在し、
  想定パターン（日付・時刻・会場の表記ゆれ）を網羅している

#### FR-42 取り込み実行ログと消費リソースの記録

課金額と動作状況を後から追跡できるようにする。

**受入基準**

- 各実行について、開始日時・終了日時・取得リソース数・結果（成功／失敗）を記録する
- 記録から任意期間の取得リソース数を集計できる（NFR-04）
- **異常終了して実行中のまま残った記録が、以降の取り込みを恒久的に止めない**
  （多重起動防止の判定規則は `docs/x-integration.md`「多重起動の防止」）
- ログに Bearer Token を出力しない（NFR-03）

#### FR-43 取り込み失敗時のリトライと打ち切り

**受入基準**

- 429 および 5xx に対して指数バックオフでリトライする
- リトライ回数に上限があり、無限リトライしない
- **連続して失敗し続けた場合は取り込みを停止し、自動で再開しない。**
  失敗のたびに同じ範囲を取り直すため、放置すると X API の重複排除が切れて
  再課金が積み上がる（`docs/x-integration.md`「エラーハンドリング」）
- 打ち切り時も次回実行の `since_id` が壊れない（**取得済み位置が後退しない**）
- 連続失敗を管理者が検知できる（NFR-09）

## 7. 非機能要件

### NFR-01 性能

想定データ量は 1 か月あたり最大 50 件。**キャッシュに命中する経路と、
しない経路で目標を分ける。**

- **ISR キャッシュに命中する公開カレンダーの応答が p95 300ms 以内**
- **キャッシュに存在しない月の初回表示が p95 3 秒以内。** Neon はアイドルで
  コンピュートが停止するため、この経路だけコールドスタートを含む
  （`docs/architecture.md`「Neon を選んだ理由と制約」 / [architecture.md](architecture.md)「キャッシュ戦略」）
- 1 か月分のデータ取得が 1 リクエストで完結する（日付ごとにリクエストを分割しない）

### NFR-02 可用性

- X API の障害・レート制限・クレジット切れが発生しても、**公開カレンダーの閲覧は継続できる**
- 取り込み処理の失敗が公開画面のエラーとして表面化しない

### NFR-03 セキュリティ

- [CLAUDE.md](../CLAUDE.md) の「セキュリティ方針」の全項目を満たす
- 管理画面および管理 API はデフォルト拒否とし、公開エンドポイントのみを明示的に許可する
- 公開 API は `GET` のみを提供する
- ログイン試行は送信元単位で回数制限し、超過時は一定時間拒否する
- X 由来のテキスト（本文・URL・メンション）は信頼しない入力として検証・エスケープする

### NFR-04 運用コスト

- 通常運用における X API の消費額が**月 $5 を超えない**
- 消費リソース数を集計でき、想定を超えた場合に気づける（FR-42）
- **Neon のコンピュート時間が無料枠（100 CU-hours/月）に収まる。**
  取り込みジョブは閲覧者がいなくても枠を消費するため、
  そのベースラインを含めて試算する（`docs/architecture.md`「運用コストの試算」）。
  枠を超えるとコンピュートが停止しサイトが閲覧できなくなる（NFR-02）

### NFR-05 タイムゾーンと日付境界

- タイムゾーンは JST 固定とする。保存形式は用途で分ける。システムの時刻は
  `TIMESTAMPTZ` で UTC、イベントの開催日・出演時刻は `DATE` / `TIME` で
  JST のローカル値（[ADR-0005](adr/0005-local-date-storage.md)）
- 「その日の出演」の判定は **JST の 00:00:00〜23:59:59** とする
- 深夜公演（「26:00 開演」のような表記）は、**時刻が実際に属する暦日**に配置する。
  「26:00」なら開催日を翌日、出演開始時刻を `02:00` として保存する
  （[ADR-0011](adr/0011-midnight-date-rule.md)）
- 出演枠そのものが日を跨ぐ場合（「23:50-24:30」のような表記）は自動登録せず、
  未処理投稿として管理者に回す
- 月またぎ・日またぎ・深夜帯のテストが存在する

### NFR-06 レスポンシブ対応

- 幅 360px 以上の画面で、横スクロールなしにカレンダーを操作できる
- タップ対象は 44×44 px 以上を確保する

### NFR-07 将来の EAS 対応

- 公開データは HTML への埋め込みだけでなく、**JSON API から取得できる**
- API のレスポンスに Web の表示都合（HTML 断片、CSS クラス名など）を含めない

### NFR-08 アクセシビリティ

- カレンダーの月移動と日付選択がキーボードのみで完了できる
- 情報を色のみで伝えない（FR-02 と対応）
- 本文テキストのコントラスト比 4.5:1 以上

### NFR-09 ログと監視

- 取り込みの連続失敗に管理者が気づける（管理画面上の警告表示を最低ラインとする）
- ログに個人情報・認証情報・トークンを出力しない

## 8. データ要件（概要）

詳細スキーマは `docs/data-model.md` で確定させる。ここでは**何を持ち、何を持たないか**のみ定める。

### 8.1 保持するもの

| データ | 主な項目 |
| --- | --- |
| 情報源アカウント | X の username、user_id、取得済み最大 tweet_id |
| 出演情報 | 日付、イベント名（**表示用の原文**と**照合用の正規化値**を別に持つ）、会場（都道府県・ステージ名を含む）、XINXIN の出演開始／終了時刻、**物販の開始／終了時刻**、チケット URL、出典 URL、登録経路（自動／手動）、登録日時、更新日時 |
| 取り込み済み投稿の記録 | tweet_id、処理状態（登録済み／未処理／対象外） |
| 取り込み実行ログ | 実行日時、取得リソース数、結果 |

「取り込み済み投稿の記録」は、削除した出演情報が再取り込みで復活するのを防ぐために必要
（FR-23, FR-41）。定常運用では `since_id` により同じ投稿を再取得しないが、障害復旧や
初回バックフィルで再処理が起きた場合の冪等性を、この記録で担保する。

### 8.2 保持しないもの

- **投稿本文の原文**（LR-02）。抽出した事実データのみを保持する
- **画像・動画などメディアの実体**（LR-03）
- 閲覧者に関する個人情報（閲覧者アカウントが存在しないため）
- **チケット価格**。券種が多様で転記ミスのリスクが高く、誤った価格の公開は実害になる。
  `ticket_url` の先で確認してもらう
- **イベントの開場・開演時刻**（`⏰OPEN / START`）。会場全体の時刻であり、
  XINXIN の出演時刻と物販時刻が分かればファンの行動には足りる。出典 X 投稿で確認できる

### 8.3 保持期間

過去の出演情報も削除せず保持し、過去の月を遡って閲覧できる状態を保つ。
上限は現時点で設けない（本書「未決定事項（要件レベル）」の未決定事項）。

## 9. 外部依存と制約

X API v2 に依存する。料金体系と API 仕様の詳細は [CLAUDE.md](../CLAUDE.md) および
`docs/x-integration.md` に置く。要件に影響する制約は以下。

- **従量課金**（取得リソース数に対する課金）。差分取得を守らないと課金が膨らむ → FR-40, NFR-04
- **タイムラインの遡り上限は約 3,200 件**。過去分の完全な取り込みは保証できない → 非スコープ
- **レート制限（429）** が発生しうる → FR-43
- 情報源アカウントが非公開化・凍結された場合、取り込みは停止する。
  ただし登録済みの出演情報の閲覧は影響を受けない → NFR-02

## 10. 法務・コンプライアンス要件

一般公開する以上、以下は実装の必須要件として扱う。

### LR-01 非公式である旨の明示

**受入基準**: 全ページに、非公式であり XINXIN および運営と関係がない旨の記載がある（FR-07）。

### LR-02 投稿本文を転載せず、事実データに正規化して保持

**受入基準**

- 投稿本文の原文を保存するカラムが DB に存在しない
- 画面に投稿本文をそのまま表示しない
- 保持するのは日時・会場・イベント名などの事実データに限る

本要件が対象とするのは**公開されるアプリ**である。抽出テストに使う実サンプル
（`docs/x-post-sample/`）は投稿本文そのものだが、**リポジトリを外部公開しない**ため
転載にあたらない（`docs/security.md` T-07、`docs/adr/0015-private-repository.md`）。

### LR-03 画像・メディアの無断転載をしない

**受入基準**: 投稿に添付された画像・動画を保存・再配信しない。

### LR-04 出典の明示

**受入基準**: すべての出演情報から、根拠となった X 投稿へ辿れる（FR-06）。

### LR-05 削除要請への対応

**受入基準**

- サイト上に問い合わせ・削除要請のための連絡手段が記載されている。
  **手段はサイト専用のメールアドレス**とし、全ページのフッタと停止ページに出す
  （[ADR-0017](adr/0017-contact-channel.md)）。
  **停止中も到達できること。** サイト内のフォームは停止中に消えるため使わない
- 要請を受けた際、管理者が個別の出演情報を削除できる（FR-23）
- 要請を受けた際、**サイト全体を非公開にできる手段**を管理者が持つ
  （`docs/architecture.md`「サイト全体の停止」）
- 非公開にしている間は、**キャッシュ済みのページも配信されない**
- 非公開の状態でも、管理者は個別の出演情報を削除できる（FR-23）

### LR-06 X 利用規約・デベロッパーポリシーの遵守

**受入基準**: データ取得は公式 API 経由のみとし、スクレイピングを行うコードが存在しない。

## 12. 未決定事項（要件レベル）

技術的な未決定事項は [CLAUDE.md](../CLAUDE.md) の「未決定事項」を参照。ここには要件レベルのものだけを記す。

**番号で参照しない**（項目を消すと番号がずれる）。他の文書からは**項目名**で参照する。

1. **アクセス解析の導入有無**。導入する場合はプライバシーポリシーの掲示が必要になり、
   要件が増える
2. **出演情報の保持期間の上限**（現時点では無期限）
3. **抽出精度の目標水準**（FR-41）。承認フローを設けない以上、抽出精度が公開情報の
   品質を直接決める。どの水準を満たせば運用可能とみなすかを、テストデータで判断する。
   **2026-09-03 の初回バックフィルの実測: 338 件中 223 件（66%）が未処理。**
   残り 115 件から出演情報 76 件が登録された（複数の投稿が同じ公演を指し、
   空欄補完が働いた結果）。**未処理 223 件の中に告知が何件混ざっているかは
   中身を見ないと分からない。** ここが目標水準を決める材料になる
