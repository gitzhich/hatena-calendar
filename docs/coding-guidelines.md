## 0. この文書の位置づけ

**実装を始める前に読む。**

ここに書くのは「**同じ規約を別の場所で書き直したときに食い違った / 食い違いうるもの**」だけ。
一般的なスタイル（命名・整形・行長）は載せない。設計判断そのものの理由も載せない。
理由は各設計文書と ADR にあり、この文書は**実装時にどう守るか**だけを書く。

### 0.1 なぜ文書に出したか

規約をコードのコメントにだけ置くと、**そのファイルを開かない限り伝わらない**。

実例がある。「日時の表示に `toLocaleString` を使わない」という判断は
`frontend/lib/last-updated.ts` のコメントに理由まで書かれていたが、
別の画面（`frontend/app/admin/unparsed/page.tsx`）を書くときに参照されず、
禁じたはずの書き方がそのまま入った。**コメントは正しかったのに効かなかった。**

### 0.2 機械で検査しているもの

規約のうち検査できるものはテストで落ちるようにしてある。**表にあるものは、
破ると CI が赤くなる。** 表に無いものは人が守る。

| 規約 | 検査 |
| --- | --- |
| 日時をロケール依存で組み立てない（本書「日時」） | `frontend/lib/date-display.test.ts` |
| セッション Cookie を公開ページに送らない（本書「シークレットとキー」） | `frontend/lib/session.test.ts` |
| 取得範囲なしの X API 呼び出しを書けない（本書「課金に直結する値」） | `backend` `IngestionGuardrailTest` |
| 取得位置を後退させない（本書「課金に直結する値」） | 同上 |
| テストが実 X API を叩かない（本書「課金に直結する値」） | 同上 |
| 認可規則を書き忘れたパスが素通りしない（本書「公開と管理を分ける」） | `backend` `SecurityDefaultDenyIT` |
| 設計文書への参照が実在する（本書「設計文書への参照」） | `scripts/check-doc-refs.py` |

新しい規約を足すときは、**検査を書けないか先に考える**。書ければこの表に足す。

## 1. 日時

タイムゾーンは JST 固定。ただし**保存形式を 2 種類に分ける**
（[data-model.md](data-model.md)「タイムゾーンの扱い」 / [ADR-0005](adr/0005-local-date-storage.md)）。

| 種類 | 例 | 型 | 保存 | 変換 |
| --- | --- | --- | --- | --- |
| システムの時刻 | `created_at` `started_at` `finished_at` | `TIMESTAMPTZ` | UTC | 表示時に JST へ |
| イベントの暦日・時刻 | `appearance_date` `performance_start_time` | `DATE` / `TIME` | JST のローカル値 | **しない** |

後者を UTC 化するとカレンダーの月境界がずれる。暦日そのものが意味を持つ値であるため。

### 1.1 API は UTC で返す。DTO で正規化する

`TIMESTAMPTZ` を載せる DTO は、**コンパクトコンストラクタで UTC に正規化する**。

```java
public IngestionRunDto {
    startedAt = toUtc(startedAt);
    finishedAt = toUtc(finishedAt);
}
```

正規化しないと、JDBC ドライバが返すオフセット（JVM の既定タイムゾーンに依存する）が
そのまま JSON に出る。絶対時刻としては同じでも、受け取り側の変換が読みにくくなる。

**この正規化は結合テストでは守れない。** PostgreSQL の `TIMESTAMPTZ` を
`OffsetDateTime` で読むとドライバが UTC で返すため、正規化を外しても結果が変わらない。
**任意のオフセットを渡す単体テストを別に書く**（`IngestionStatusTest` /
`IngestionRunQueryTest`）。FR-08 の実装時、これを怠って変異が素通りした。

### 1.2 表示側は `formatJst` を使う

`toLocaleString` / `toLocaleDateString` / `toLocaleTimeString` / `Intl.DateTimeFormat`
で日時を組み立てない。実行環境のタイムゾーン設定と ICU データに依存し、
**ICU が同梱されない構成では `timeZone` の指定が黙って無視される**。
例外にならず、9 時間ずれた時刻がそのまま表示される。

`frontend/lib/last-updated.ts` の `formatJst` を使う。オフセットを足して UTC の
ゲッターで読むため、どの環境でも同じ値になる。

数値の桁区切り（`count.toLocaleString("ja-JP")`）はタイムゾーンに関係しないため対象外。

### 1.3 深夜公演は時刻が実際に属する暦日に置く

「26:00 開演」は開催日を翌日、開始時刻を `02:00` として保存する
（[ADR-0011](adr/0011-midnight-date-rule.md)）。
出演枠自体が日をまたぐ表記（「23:50-24:30」）は自動登録せず未処理に回す。

### 1.4 日付境界のテストを必ず書く

月またぎ・日またぎ・深夜帯・**JST と UTC で答えが変わる時刻**を含める。
「当月」のような相対的な時刻は `Clock` ビーンを差し込んで固定する
（`ClockConfig` / テストは `MovableClock`）。実時刻に依存させると、
**特定の日にだけ落ちるテスト**になる。

## 2. 判定は 1 か所に置く

**同じ判定を 2 か所に書かない。** 条件がずれても誰も気づけないため。

| 判定 | 正本 | 使う側 |
| --- | --- | --- |
| データが古いか（`stale`） | `IngestionStatusService.isStale` | 公開 API → 画面はそのまま表示 |
| 取り込みが打ち切られたか（`halted`） | `IngestionHaltRule` | `IngestionService` と管理 API |

### 2.1 フロントで再判定しない

サーバが返した真偽値をそのまま表示する。閾値をフロントに複写すると、
サーバ側を変えたときに画面だけ古い基準で出続ける。

### 2.2 一覧の中身を数え直さない

`halted` を「表示中のページの `items` に失敗がいくつあるか」で求めない。
ページを送ると答えが変わる。判定はサーバが直近の実行から求める。

### 2.3 規則と、その規則が必要とする値を同じ場所に置く

`IngestionHaltRule` はしきい値（`MAX_CONSECUTIVE_FAILURES`）と、
判定に使う件数（`window()`）の**両方**を持つ。判定が「直近 N 件がすべて失敗」で
ある以上、DB から取る件数が N を下回ると打ち切りが**永久に成立しない**。

リポジトリのメソッド名に件数を焼き付けない（`findTop10ByOrderByStartedAtDesc` は
この理由でやめた）。名前に埋めると、しきい値だけ変えて取得件数が追従しない事故が起きる。

## 3. 公開と管理を分ける

### 3.1 コントローラを分ける

公開用と管理用でクラスを分ける。**公開側のクラスに更新系メソッドを書かない**
（[architecture.md](architecture.md)「設計上の原則」）。分けておけば、
公開クラスに `@PostMapping` が現れた時点でレビューで気づける。

命名は `PublicXxxController` / `AdminXxxController`、DTO は
`PublicXxxDto` / `AdminXxxDto`、更新の入力は `XxxCommand`。

### 3.2 デフォルト拒否

`SecurityConfig` は `anyRequest().denyAll()` で終わる。公開するパスだけを明示的に許可する。
**新しいコントローラを足したら、認可規則も足す。** 書き忘れれば通らなくなる（安全側に倒れる）。

公開 API は `GET` のみ許可する。メソッドを指定しない許可を書かない。

### 3.3 サービス層でも認可を意識する

読み取り専用で誰でも見られるデータなら、サービス層では入力検証だけでよい。
その場合は**なぜ認可検証をしないかをクラスの javadoc に書く**
（`AppearanceService` / `IngestionRunQueryService` がその形）。
黙って省くと、後から読んだ人が「書き忘れ」と区別できない。

## 4. シークレットとキー

- **内部 API キーは公開用と管理用の 2 種類**（[ADR-0010](adr/0010-split-api-keys.md)）。
  管理キーは**管理者セッションの検証に成功したときだけ読み込む**。
  公開ページのレンダリング経路からそのモジュールを呼ばない
- `NEXT_PUBLIC_` を付けた環境変数でバックエンド URL や API キーを扱わない。ブラウザに露出する
- キーの比較は**固定時間**で行う（`ApiKeyFilter`）。`String#equals` は
  不一致で打ち切るため、応答時間の差から 1 文字ずつ推測されうる
- セッション Cookie の `path` は `/admin`。**`set` と `delete` で同じ定数を使う**
  （[ADR-0016](adr/0016-static-csp-public-nonce-admin.md)）。食い違うとログアウトで消えない
- ログ・エラーレスポンス・DB の `error_summary` にトークンとスタックトレースを入れない

## 5. 課金に直結する値

X API は**返ってきたリソース数**に課金される。次の値は金額に直結するため、
触るときは影響を書き出してから変える。

- **`since_id` を必ず渡す。** 「全件取り直し」を実装しない。
  取得範囲は `FetchWindow`（sealed）で表現し、**範囲なしの取得を型として作れない**ようにしてある
- **`last_fetched_tweet_id` を後退させない。** 前進のときだけ更新する
- 失敗のたびに同じ範囲を取り直すため、**連続失敗は打ち切る**（`IngestionHaltRule`）。
  自動で再開しない。再開のボタンを API にも画面にも置かない
- **テストから実 X API を叩かない。** スタブか記録済みレスポンスに対して行う

上 4 つはいずれも `IngestionGuardrailTest` が検査している。
規約を緩めたくなったら、まずそのテストが何を守っているかを読む。

ローカルで `bootRun` を止め忘れると 30 分ごとに取り込みが走る。
取り込みを動かす意図がない確認では `--ingestion.enabled=false` を付ける。

## 6. フロントエンドの境界

### 6.1 `server-only` を付ける基準

**モジュール自身が秘密を読むなら付ける。** 読まないなら付けない。

| 例 | `server-only` | 理由 |
| --- | --- | --- |
| `frontend/lib/admin-api.ts` `frontend/lib/api.ts` | **付ける** | 内部 API キーを読む |
| `frontend/lib/backend-url.ts` `frontend/lib/rate-limit.ts` | 付けない | 秘密を持たない。付けると `node --test` から読めない |
| `frontend/lib/session.ts` | 付けない | `frontend/proxy.ts`（Edge）と Server Component の両方から使う |

付けない場合は、**その判断と、サーバ境界を誰が守るかをファイル冒頭に書く**。
書かないと「付け忘れ」と区別できない。

### 6.2 `node --test` から読むモジュールの相対 import は `.ts` を付ける

```ts
import { createRateLimiter } from "./rate-limit.ts";   // 単体テストから辿る
import { backendBaseUrl } from "./backend-url";        // Next.js 経由のみ
```

Node の型剥がしは拡張子を補完しない。付け忘れると `npm test` だけが落ちる
（`frontend/tsconfig.json` の `allowImportingTsExtensions` で許可してある）。

### 6.3 ブラウザから Spring Boot を直接呼ばない

すべて Next.js を経由する（[ADR-0008](adr/0008-nextjs-bff.md)）。
フロントエンド固有のロジックをバックエンドに埋め込まない。
Web の API 契約をそのままモバイルから叩けるようにしておく。

## 7. キャッシュ

| 対象 | 指定 | 理由 |
| --- | --- | --- |
| 公開ページ | `export const revalidate = 300` | 閲覧アクセスを DB まで届かせない |
| 動的セグメント | 上に加えて `generateStaticParams` | **無いと純粋な動的レンダリングになり `no-store` で毎回 DB に届く** |
| 管理画面 | `export const dynamic = "force-dynamic"` / `cache: "no-store"` | セッションを読むため |

ISR は性能だけでなく**可用性の防御**でもある。Neon の無料枠を公開ページの連打で
枯渇させられるとサイトが止まる（[security.md](security.md) T-04）。
**ISR を外す変更は、この防御を外す変更**として扱う。

**`generateStaticParams` が空配列を返していても消さない。** 静的最適化の対象に
入れるための宣言であり、返す値の中身とは別の意味を持つ。

年月の範囲は有限にする（[ADR-0014](adr/0014-bounded-calendar-range.md)）。
範囲外は**データを取得する前に** 404 にする。

管理操作で公開ページを更新したら `revalidatePath` を呼ぶ。

## 8. 入力検証とエラー応答

- **サーバ側検証を正とする。** フロント側検証は UX のためのもの
- 入力の形式は Bean Validation で `XxxCommand` に宣言する。
  業務規則（範囲・重複）はサービス層で検証する
- **検証を通ってから DB を引く。** 範囲外の入力で DB へ到達させないこと自体が防御になる
- SQL は JPA / パラメータバインドのみ。文字列連結でクエリを組み立てない
- エラーは RFC 7807（`ProblemDetail`）で返す。
  **スタックトレース・SQL・内部のクラス名をレスポンスに含めない。** 詳細はログにのみ残す
- 未認証と認可失敗をどちらも `403` にする。`401` を返すと
  「キーが無い」と「キーが違う」を区別できてしまう
- X 由来のテキストは**信頼しない入力**として扱う。`dangerouslySetInnerHTML` を使わない

## 9. 表示とアクセシビリティ

- **色だけで意味を伝えない。文言で伝える**（NFR-08）。
  警告は「何が起きているか」と「何をすればよいか」を文章で書く
- タップ対象は 44px 以上。リンクとボタンに `min-h-11` を付ける（NFR-06）
- 値が無い項目は**欄ごと出さない**。空欄を並べない。
  **例外:** 出演時刻が無いときは「時刻未定」と出す（FR-04）
- 日時には `<time dateTime={iso}>` を付ける。`dateTime` には UTC の原文を入れる
- **公開ページを新しく足したら `Disclaimer` を置く**（LR-01：全ページに非公式である旨の記載）。
  現状は `frontend/components/CalendarPage.tsx` の中に 1 箇所あるだけで、
  そこを通らないページには付かない

## 10. テストの書き方

### 10.1 何をどこで確かめるか

| 確かめたいこと | 置く場所 |
| --- | --- |
| 判定規則・境界・整形 | 単体テスト（DB も HTTP も通さない） |
| API の形・認可・永続化 | 結合テスト（Testcontainers） |
| 「こう書いてはいけない」という規約 | ソースを読む検査（本書「機械で検査しているもの」） |

**結合テストで守れないものを結合テストに置かない。** 本書「API は UTC で返す。DTO で正規化する」の UTC 正規化が例で、
DB を通すとドライバが吸収してしまい、実装を壊しても落ちない。

### 10.2 入力は本番で実際に現れる形にする

**きれいな値を選ぶと、実装が壊れていても差が出ない。**

このリポジトリで**繰り返し起きている失敗**がこれで、通っているテストが
規約を守っていない例が何度も出ている。共通しているのは
「**テストの入力が、本番で実際に流れる値の形をしていなかった**」ことである。

| 起きたこと | 使っていた入力 | 本番で流れる値 | 結果 |
| --- | --- | --- | --- |
| `start_time` がナノ秒付きで送られ X API が **HTTP 400** | `OffsetDateTime.of(…, 0, UTC)`（ナノ秒 0） | `OffsetDateTime.now()` は**必ずナノ秒を持つ** | バックフィルが**一度も成功しえない**状態で出荷 |
| 概算コストの丸めを外す変異が素通り | 1 / 287 / 300 / 1000 | 0〜5000 の**822 件**で丸め方により結果が変わる | 丸めが効いているか検証していなかった |
| 日時の UTC 正規化を外す変異が素通り | DB 経由の値 | ドライバが UTC で返すため**差が出ない** | 結合テストでは守れない（本書「何をどこで確かめるか」） |

**次を疑う。**

- **時刻**: `now()` は秒未満を持つ。0 で作った値はその扱いを試さない
- **境界**: 上限ちょうど、1 つ手前、空、1 件、最大件数
- **丸めと桁**: 端数が出る値を含める。切り上げと切り捨てで**答えが変わる値**を選ぶ
- **文字**: 実データには絵文字・全角空白・改行が入る（`docs/x-post-sample/`）

**「この入力なら、実装を壊したときに結果が変わるか」を書く前に自問する。**
変わらないなら、その入力ではテストになっていない。

### 10.3 外部へ送る値は末尾まで検証する

**値の途中までしか書かないと、後ろに何が付いても通る。**

```java
// 素通りした形：start_time=2026-06-02T00:00:00.021243663Z でも通る
assertThat(uri).contains("start_time=2026-06-02T00:00");

// 直した形：値を末尾まで書く
assertThat(uri).contains("start_time=2026-06-02T00:00:00Z");
```

**問題は `contains` を使ったことではない。** URI は他のパラメータも含むので
`contains` になるのは自然で、**書いた値が途中で切れていたこと**が問題だった。

外部 API へ送るクエリ・ヘッダ・本文は、**受け取る側が形式を検証する**。
こちらのテストが緩いと、**本番で初めて 400 が返る**。

「**含まれていること自体**が要件」なら、キーだけの部分一致でよい
（`exclude=replies,retweets` が付いているか、など）。
**値の形が問われるものは、区切り文字まで含めて末尾まで書く。**

### 10.4 変異テストで確かめる

テストが本当に退行を捕まえるかは、**実装をわざと壊して確かめる**
（`scripts/mutation-test.py`。CLAUDE.md の「変異テスト」）。

**本番で実際に起きた誤りは、それ自体を変異として登録する。** 直したつもりが
戻ったときに落ちる。`start_time` の件では
「`OffsetDateTime` をそのまま渡す」を変異にして検出を確かめた。

### 10.5 テストは開発用 DB を使わない

Testcontainers が使い捨ての PostgreSQL を実行ごとに立てる（`PostgresContainerListener`）。
接続先とプール上限もそこが決める。**テストクラス側に何も足さない。**
継承や `@Import` を要求すると、付け忘れた 1 クラスが開発用 DB を触りにいく。

設定の違う結合テストを足すと Spring のコンテキストが 1 つ増え、
それぞれが接続プールを握る。**`max_connections` に届くと、
原因と無関係のクラスが落ちる。**

## 11. 定数の置き場所

- **意味を持つ数値を式の中に直接書かない。** 名前を付けて定数にする
- 定数は**それを解釈する側**に置く。しきい値はその判定を行うクラスへ
- 同じ値を 2 か所に書かない。片方だけ変わる
- 単価・上限のように**外部の事情で決まる値**は、出典をコメントに書く
  （例: `USD_PER_RESOURCE` は X API の Posts: Read の単価）

## 12. 設計文書への参照

コメントや文書から設計文書の節を指すときは、**位置ではなく同一性で書く**。

| 指す先 | 書き方 |
| --- | --- |
| 要件・脅威・ADR | `FR-08` `NFR-03` `LR-02` `T-01` `ADR-0020` — **ID があるものは必ず ID** |
| 他の文書の節 | `docs/x-integration.md「日付」`（コードから）<br>`[data-model.md](data-model.md)「タイムゾーンの扱い」`（文書から） |
| 同じ文書の中の節 | `本書「未決定事項」` |

### 12.1 章・節番号で参照しない

**番号は文書を並べ替えるだけでずれる。** しかも壊れ方が悪い。
章を 1 つ挿し込むと `第 9 章` は `第 9 章` のまま存在し続け、
**参照は解決するのに指す先だけが別物になる**。リンク切れと違って気づけない。

見出しテキストなら、見出しが変われば参照は**必ず**解決不能になる。
壊れたことが分かるほうが、壊れていないように見えるより良い。

このリポジトリでは振り直しが 4 回起きており、`x-integration.md` の
`11.2 → 11.1` で `PostParserSampleTest` の参照が実際に 1 件壊れていた。

### 12.2 文書名は参照と同じ行に置く

`第 5.12 節` のように文書名を伴わない参照は、**人間には読めても機械には解決できない**。
`PostParser.java` の裸の参照は、直前に現れる文書名が `architecture.md` で、
実際の対象である `x-integration.md` ではなかった。検査が書けないものは守れない。

`「見出し」` の直前に文書名が無いものは参照として扱われない。
本文中の普通の鉤括弧を拾わないためにそうしてある。

### 12.3 手順番号はそのまま使う

`runbook-*.md` の「手順 3」は章の位置ではなく**作業の順序そのもの**を指す。
「手順 3 を手順 4 より先に」は番号でしか書けないため、これは対象外。
節の中の番号付きリストを指す「手順 3」も同じ。

### 12.4 検査

```bash
scripts/check-doc-refs.py     # CI の docs ジョブが実行する
```

見出しの実在、番号参照の残存、要件 ID と ADR の実在を検査する。
**見出しを変えた変更は、その PR の中でコメント側も直すことになる。**
実装ファイルに参照が散らばっていても見落とせない。

対象は `git ls-files` が返す**追跡ファイルだけ**。`.env` は `.gitignore` で
追跡外なので読まれない。加えて、シークレットが入りうる名前のファイル
（`.env*` / `*.pem` / `application-local.*` など）は、指摘を出すときに
**行の中身を出さない**。検査結果は CI のログに残るため、誤ってコミットされた
場合でも値がログへ写らないようにしてある。

## 13. この文書の更新

規約が増えたとき、**コードのコメントだけで済ませない**。
食い違いが起きうるものはここに足し、検査を書けるなら本書「機械で検査しているもの」の表にも足す。
